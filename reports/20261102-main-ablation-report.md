# FormSy SOP 新仓库 main 消融实验报告

日期：2026-11-02。案例：设计稿送审与客户确认工具，第一阶段。

## 结论

本轮 3 组 × 3 seed 的消融没有显示 `origin/main` SOP 对该案例第一阶段形成稳定优势。人工按冻结标准评审后：

| 组 | seed 事实覆盖（满分 8） | 缺陷数（越小越好） | 主要表现 |
|---|---:|---:|---|
| Baseline | 6、8、8 | 4、3、2 | 事实承接较完整，但重问已定事实、引入扩展建议；seed42 对自动发布不清楚 |
| NeutralLong | 5、7、6 | 4、3、2 | 稳定性较差，自动发布和旧版只读常缺失，且存在范围膨胀 |
| MainSOP | 8、8、6 | 0、1、3 | seed42/43 明显更好，seed44 退化为管理员/通知/备份等范围膨胀 |

MainSOP 最重要的正向差异不是模板更完整，而是两点：

1. seed42 输出没有重问已定事实、没有明显范围膨胀，且 8 项事实全部清楚，是 9 条中唯一达到“高事实保真 + 0 缺陷”的结果。
2. seed42/43 均把“客户确认人”和“其他客户”的权限边界写清楚，比多数 Baseline/NeutralLong 结果更接近业务关键差异。

但 MainSOP seed44 明显退化：自动发布不清楚、旧版本只读弱化，还引入了管理员、通知、备份恢复、历史恢复等未给能力。因此不能把结果表述为“MainSOP 全面提升”。更准确的结论是：main SOP 在该模型上能提高好结果的上限，但没有解决 14B 模型在同一提示下的执行不稳定。

## 与长提示效应的关系

NeutralLong 用来排除“只是提示更长”的影响。它的长度与 main 资源对齐（37,610 字符 vs 37,576 字符），但内容为通用设计建议。实际结果为 5、7、6 分，且三条均有范围膨胀或重问问题。这说明长提示本身没有带来稳定收益，MainSOP seed42/43 的改善不能简单归因于 prompt 长度。

不过 NeutralLong 的字符数对齐不等于 token 数完全一致：真实 tokenizer 结果为 Baseline 572 tokens，NeutralLong 24,039 tokens，MainSOP 20,512 tokens。MainSOP 比 NeutralLong 短约 3,527 tokens。这个差异已保留在预算审计中，没有做截断或改写，因此它仍是内容对照组，不是严格的 token 等长对照。

## 运行环境与资源修复

最初按原协议使用 `-ngl all`、默认 batch 2048/512、32K 上下文运行，连续触发 Apple Metal `Insufficient Memory`。排查发现：

1. 第一次 OOM 期间存在旧的正式 runner 持续启动并发模型进程，已停止并保留失败记录。
2. 停止并发后，8K 上下文仍 OOM，说明不是单纯上下文或旧进程问题。
3. CPU smoke test 可以生成，但 127 tokens 用时 372 秒，不适合完整实验。
4. 20 层 GPU 混合模式在 24K/32K 长 prompt 上预填充过慢或超时。
5. 模型文件曾被用户清理，已按官方 revision 重新下载，SHA-256 验证为：
   `500a8806e85ee9c83f3ae08420295592451379b4f8cf2d0f41c15dffeb6b81f0`。
6. 最终保留全 GPU 层和 32K 上下文，只将 batch 降为 256、ubatch 降为 128。最长 prompt smoke test 通过，未再 OOM。

该 batch 参数是运行时适配项，不在原协议中。三组 9 条均使用完全相同配置，因此组间可比；但与旧实验的绝对输出不可直接对比。

## 盲评与复核

推理后先随机匿名化为 R01–R09，thinking 另行匿名化为 T01–T09，映射保存在 `盲评映射-sealed.json`。自动预检只使用正则识别候选证据，人工复核逐条确认。自动预检显示所有输出均存在“关键反例缺失”的候选标记，但人工复核发现 seed42/43 等输出实际包含较多反例，因此最终结论只采用人工复核结果。

人工复核显示：

- MainSOP seed42：8/8 事实清楚，0 缺陷，是本轮最佳样本。
- MainSOP seed43：8/8 事实清楚，1 缺陷，主要是云存储、SVG、通知、版本回滚等未给能力。
- MainSOP seed44：6/8，3 缺陷，出现管理员、通知、备份恢复等范围膨胀。
- Baseline seed43/44 达到 8/8，说明模型在该案例上本身能力较强；SOP 的增益主要体现在减少 seed42 类输出的重问和范围膨胀，而不是让所有 seed 都稳定。

## 边界

1. 本实验只覆盖一个真实案例第一阶段和 3 个 seed，不能做统计显著性检验。
2. MainSOP 是宿主注入 8 个资源文本，不是模型自主调用仓库、工具或工作台。
3. 评审是静态设计文档评审，没有代码实现、测试、部署或用户验收。
4. batch 参数因本机资源限制调整，三组内部可比，但不能与旧 32K 默认 batch 实验直接比较。
5. NeutralLong 是字符等长、通用内容对照，不是严格 token 等长对照。

## 对 SOP 的改进建议

1. **增加“已定事实不得降级”规则**：凡题面已明确的事实，不允许放入“待确认问题”。该问题在 Baseline 和 NeutralLong 中高频出现，MainSOP 有改善但 seed43 仍有未给能力建议。
2. **增加“扩展能力必须标记为建议”规则**：云存储、通知、归档、版本对比、批量上传、历史恢复等若非已定事实，应统一写入“建议，不进入本期范围”，避免任务膨胀。
3. **保持“审核通过即发布”单一动作**：技术接口不得把审核与发布拆成两个独立入口，除非明确说明这是内部事务边界。
4. **强调版本是确认/意见的权限载体**：接口应使用 version_id，而不是仅 design_id；否则旧版只读、新版本不继承确认等规则容易在实现层失效。
5. **加强 seed 稳定性检查**：MainSOP seed44 的退化说明，仅靠长 SOP 不能保证执行一致。建议后续把“同一提示 3 seed 一致性”作为 SOP 版本验收项。
