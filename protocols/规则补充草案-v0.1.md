# FormSy SOP 规则补充草案 v0.1

日期：2026-11-02。状态：草案，未批准、未合入仓库。来源：`origin/main` 消融实验中 Baseline、NeutralLong、MainSOP 的实际失败模式。

## 1. 设计目标

这批补充规则只解决四类已观察到的稳定问题：

1. 已定事实被降级为待确认问题。
2. 未给能力被写成实施任务或数据模型。
3. “审核通过即发布”等业务等价规则在接口层被拆散。
4. 版本、确认、意见、权限之间的对象边界在技术设计中丢失。

目标是让 SOP 更像“事实与边界守门器”，而不是继续增加通用写作模板。所有新规则都应有触发条件，未触发时不要加载，避免提示继续膨胀。

## 2. 与现有规则的关系

现有 main 规则已经覆盖大方向：

- PC03 覆盖范围与优先级。
- PC04 覆盖来源、假设与未知。
- PC08 覆盖业务规则与状态。
- PC10 覆盖数据、权限与副作用。
- PC12 覆盖验收设计。
- TC01 覆盖基线与有效决定。
- TC04 覆盖接口契约。
- TC06 覆盖状态与场景。
- TC09 覆盖权限与副作用。

因此本草案不新增平行规则体系，而是给现有 PC/TC 增加“子规则”。子规则编号采用 `PCxx.y`、`TCxx.y`，不改变 PC01–PC15、TC01–TC15 的原编号和兼容性。

## 3. 补充规则草案

### PC03.1 事实等级冻结

触发条件：任务输入中存在用户已确认的事实、决定或验收口径。

要求：

1. 输出前先把输入分为四类：
   - 已确认事实：用户或有效决定明确给出。
   - 用户假设：用户提出但标明是假设。
   - 模型建议：模型或资料补充的建议。
   - 真未知：资料缺失且影响设计。
2. 已确认事实不得放入“待确认问题”。若确需追问，只能追问缺失边界，不得重问该事实是否成立。
3. 输出中每条关键已确认事实必须能定位到承接位置，建议使用“事实承接表”。
4. 已确认事实之间冲突时，停止推进并列出冲突原文；不得静默选择其一。

建议输出字段：

| 事实 ID | 已确认内容摘要 | 来源 | 输出承接位置 | 状态 |
|---|---|---|---|---|
| F01 | 审核通过即自动发布 | 用户输入 | 状态机 / API / 验收 | 已承接 |

不满足示例：

- 用户已说“每项目指定一名客户确认人”，输出仍问“客户确认人是否唯一”。
- 用户已说“审核通过即自动发布”，输出问“审核通过后是否需要发布”。

### PC03.2 范围增量守门

触发条件：输出中出现输入未给定的角色、能力、服务、通知、归档、备份、恢复、批量操作、管理员、自动化或存储策略。

要求：

1. 新增内容必须标记为“候选建议”，不得进入实施任务、接口清单或数据模型。
2. 明确说明其不在当前确认范围内，需用户确认后才升级为需求。
3. 技术上必须为了实现已确认事实而引入的内部机制，标记为“技术必要”，并说明与哪个已确认事实相关。
4. 不因通用最佳实践自动新增能力。

判定顺序：

1. 是否来自用户原文或有效决定？
2. 是否是实现某条已确认事实的技术必要条件？
3. 是否只是模型建议？

只有第 1 类进入范围；第 2 类进入技术设计并标注来源；第 3 类进入“候选建议，不进入本期范围”。

不满足示例：

- 输入未给管理员，却设计“管理员管理项目成员”。
- 输入未给自动通知，却列“通知模块”实施任务。
- 输入未给云存储，却把云存储作为默认方案。

### PC08.1 业务动作等价性

触发条件：已确认事实使用“即”“自动”“同时”“不得”“只”“仅”等强业务语义，或规定两个动作对外表现为一个结果。

要求：

1. 产品状态机和验收必须把该规则作为一个对外业务动作或一个原子状态转换承接。
2. 技术上可以拆成内部步骤，但中间状态不得暴露给用户，且失败时不得留下违反业务语义的状态。
3. API 不得把已确认的等价动作拆成两个外部可选步骤，除非用户明确要求分步。
4. 验收必须覆盖成功转换和失败回滚/错误保留行为。

示例：

- 已确认“审核通过即自动发布”：不得同时提供 `/approve` 和 `/publish` 两个由负责人自由调用的外部接口；可设计内部审核记录和发布事务，但对外结果必须是审核通过后版本已发布。

### PC10.1 权限所有者矩阵

触发条件：同一对象存在多种角色，或同一动作存在不同权限结果。

要求：

1. 每个动作必须写清：动作、对象、允许执行者、前置状态、成功结果、拒绝结果。
2. 区分查看、下载、提意见、确认、审核、发布、撤销访问等动作；不得把不同权限合并成“客户都可以”。
3. 拒绝路径必须可见，并进入验收。
4. 权限规则必须绑定到具体对象版本或对象状态，不得只写“客户可确认”。

建议矩阵：

| 动作 | 对象 | 允许执行者 | 前置状态 | 成功结果 | 拒绝结果 |
|---|---|---|---|---|---|
| 确认版本 | 最新已发布版本 | 指定客户确认人 | 意见已处理 | 记录确认 | 非确认人收到权限错误 |

### PC12.1 规则反例验收

触发条件：已确认事实包含权限、状态、版本、顺序或副作用规则。

要求：

1. 每条关键规则至少设计一个违反该规则的反例。
2. 反例不是越多越好，按规则类型触发：
   - 项目隔离规则：跨项目访问。
   - 版本规则：旧版本操作、新版本状态继承。
   - 权限规则：非授权角色操作。
   - 顺序规则：前置条件未满足就操作。
   - 副作用规则：撤销访问后已产生的外部副本。
3. 反例必须写明期望拒绝或期望不变量，不得只写“验证失败”。

### TC01.1 决定台账

触发条件：设计依赖用户决定、历史确认、评审结论或业务口径。

要求：

1. 每条关键决定记录：决定 ID、来源、原文或摘要、版本、适用范围。
2. 后续设计引用决定 ID，不靠重复叙述。
3. 输入版本变化后，复核决定是否仍适用；不自动沿用旧决定。
4. 冲突决定不得被新输出覆盖，必须保留并暴露。

### TC04.1 版本绑定接口

触发条件：业务规则涉及版本、历史、只读、确认不继承、意见绑定或状态随版本变化。

要求：

1. 意见、确认、查看、下载、审核、发布等接口必须明确作用对象是具体版本还是设计稿。
2. 规则作用对象是版本时，接口和数据模型必须使用版本 ID；不得只用设计稿 ID 代替。
3. 新版本发布时必须定义状态重置矩阵：哪些状态保留，哪些状态重置，哪些历史记录只读。
4. 旧版本的可执行动作与不可执行动作必须分别列出。

状态重置矩阵示例：

| 字段/状态 | 新版本发布后 |
|---|---|
| 旧版本文件 | 保留，只读 |
| 旧意见 | 保留，只读 |
| 旧确认记录 | 保留，不代表新版本确认 |
| 新版本确认状态 | 重置为未确认 |
| 新版本意见入口 | 开放 |

### TC06.1 状态所有者

触发条件：状态由多个动作或多个角色影响。

要求：

1. 每个状态有唯一写入方或明确的事务边界。
2. 状态转换写清前置状态、触发事件、后状态、失败状态。
3. 不允许两个角色同时拥有同一状态的最终写入权，除非已定义协同规则。
4. 对外可见状态和内部处理状态分开。

### TC09.1 副作用边界

触发条件：存在下载、导出、分享、通知、撤销访问、删除或外发能力。

要求：

1. 明确哪些副作用可撤销，哪些不可撤销。
2. 撤销访问只影响系统内后续访问，不声称能收回已下载副本。
3. 不可撤销副作用必须在用户可见流程中说明。
4. 验收覆盖“撤销后系统内不可访问”和“已下载副本仍存在”两个断言。

## 4. 执行方式建议

### 4.1 不建议把全部规则原文塞进 prompt

消融实验显示，MainSOP seed44 出现明显退化。继续增加规则原文可能加重执行不稳定。建议拆成两层：

1. **生成前事实卡**：从当前输入提取已确认事实、关键边界和触发规则，压缩成短卡，放在 prompt 前部。
2. **审查层规则**：完整 PC/TC 子规则只在工作台或自检阶段加载，用于逐项复核，不要求模型一次性记住全部条文。

事实卡建议格式：

```text
【必须承接的已确认事实】
F01 审核通过即自动发布。
F02 新版本发布后旧版本只读。
F03 每项目指定一名客户确认人，其他客户可提意见。

【禁止自动扩展】
云存储、通知、管理员、归档、版本对比、批量上传未确认，只能作为候选建议。

【触发规则】
PC08.1 业务动作等价性。
TC04.1 版本绑定接口。
PC10.1 权限所有者矩阵。
```

### 4.2 生成后审查顺序

建议固定为：

1. 事实承接：每条已确认事实是否有明确位置。
2. 事实降级：是否把已确认事实放入待确认。
3. 范围增量：是否有未确认能力进入任务/接口/数据模型。
4. 动作等价：强语义规则是否被拆散。
5. 版本绑定：版本规则是否落到版本 ID。
6. 权限矩阵：角色动作是否逐项区分。
7. 反例验收：关键规则是否有对应反例。

### 4.3 SOP 版本验收建议

新增或修订这类守门规则后，不应只跑单样本。建议最低验收：

1. 同一案例、同一模型、3 seed 重复。
2. 至少一个多角色版本流案例和一个含不可撤销副作用案例。
3. 每条规则至少被一个正例和一个反例触发。
4. 比较指标：
   - 已定事实承接率。
   - 已定事实降级次数。
   - 范围膨胀次数。
   - 状态/权限所有者错误数。
   - 关键反例覆盖率。
   - seed 间结果稳定性。

## 5. 待用户确认的问题

1. 子规则编号是否采用 `PCxx.y` / `TCxx.y`，还是希望合入现有 PC/TC 条文？
2. 事实承接表是否要求所有阶段必填，还是只在需求、技术规划和验收阶段必填？
3. 候选建议是否允许出现在最终交付中，还是必须单独放在“后续建议”附录？
4. 版本绑定接口规则是否作为硬规则，还是在无版本对象的项目中自动不适用？
5. 是否把 3 seed 稳定性纳入 SOP 版本发布门槛？

## 6. 边界

本草案尚未修改 `formsy-sop` 仓库，也未运行新版本对比实验。它只是基于当前 main 消融结果提出的规则设计稿。合入前需要完成：

1. 与 main 现有规则逐条去重。
2. 确认工作台规则编译兼容性。
3. 设计规则触发条件。
4. 用旧 main 作为对照重新做消融。
