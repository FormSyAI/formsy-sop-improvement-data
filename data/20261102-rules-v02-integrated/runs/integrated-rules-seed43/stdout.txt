# 设计稿送审与客户确认工具设计方案

## 一、业务理解
### 1.1 核心流程
系统支持三类用户角色（设计师/项目负责人/客户）通过网页端完成以下闭环流程：
```
[设计师上传设计稿] → [负责人审核发布] → [客户查看/提意见] → [负责人处理意见] → [客户确认/申请修改] → [循环迭代]
```

### 1.2 关键业务规则
- **版本管理**：每个设计稿有独立版本线，新版本发布后旧版本保持只读状态
- **权限隔离**：客户仅能查看自己项目内已发布的版本，历史版本和意见对所有人可见
- **确认继承**：旧版本确认状态不继承至新版本，需重新确认
- **意见关联**：所有修改意见必须绑定具体设计稿ID+版本号
- **修改流程**：客户确认后需通过正式申请开启新版本迭代，原确认记录保留并标注"后续修改"

## 二、规则与未知
### 2.1 明确规则
| 规则项 | 具体描述 |
|-------|---------|
| 版本隔离 | 新版本发布后，旧版本变为只读状态，但历史意见和确认记录保留 |
| 权限边界 | 客户仅能查看自己项目内已发布的版本，其他版本需负责人权限授权 |
| 意见绑定 | 所有修改意见必须关联具体设计稿ID和版本号，禁止模糊指代 |
| 确认继承 | 旧版本确认状态不自动继承至新版本，需重新确认 |
| 修改流程 | 客户确认后需通过正式申请开启新版本迭代，原确认记录保留并标注"后续修改" |

### 2.2 待确认问题
1. **多客户协作**：当项目有多个客户时，是否允许不同客户对同一设计稿提出不同意见？
2. **匿名意见**：是否允许客户匿名提交修改意见？
3. **设计稿存储**：图片/PDF等文件采用本地存储还是云端存储？
4. **版本控制**：设计稿版本号采用自增数字还是语义化版本号（如1.0.0）？
5. **撤销访问**：撤销访问权限后，已下载的文件是否需要保留访问记录？

## 三、关键状态及权限
### 3.1 用户角色权限矩阵
| 角色 | 上传设计稿 | 审核发布 | 查看所有版本 | 提交意见 | 确认版本 | 申请修改 |
|------|------------|----------|--------------|----------|----------|----------|
| 设计师 | ✅         | ❌       | ❌           | ❌       | ❌       | ❌       |
| 负责人 | ✅         | ✅       | ✅           | ✅       | ✅       | ✅       |
| 客户   | ❌         | ❌       | ✅(已发布)   | ✅       | ✅       | ✅       |

### 3.2 状态机设计
```
[设计稿] 
  ├─ 状态：待审核 → 审核通过 → 已发布 → 已归档
  │     └─ 审核不通过 → 回退至待审核
  │
  └─ 版本：v1.0 → v1.1 → v1.2 (每个版本独立状态)
```

## 四、数据与接口
### 4.1 核心数据模型
```mermaid
erDiagram
    PROJECT -->|< DESIGN_DRAFT : 包含
    DESIGN_DRAFT -->|< VERSION : 包含
    VERSION -->|< COMMENT : 关联
    VERSION -->|< CONFIRMATION : 关联
    PROJECT -->|< CUSTOMER : 包含

    DESIGN_DRAFT {
        id: 主键
        project_id: 项目ID
        creator_id: 创建者ID
        status: 状态 (待审核/已发布/已归档)
    }

    VERSION {
        id: 主键
        draft_id: 设计稿ID
        version_num: 版本号
        file_url: 文件存储路径
        status: 状态 (待审核/已发布)
        published_at: 发布时间
    }

    COMMENT {
        id: 主键
        version_id: 版本ID
        author_id: 提交者ID
        content: 意见内容
        page_number: PDF页码(可选)
        created_at: 提交时间
        resolved_at: 处理时间(可选)
        resolution: 处理结果
    }

    CONFIRMATION {
        id: 主键
        version_id: 版本ID
        confirmed_by: 确认者ID
        confirmed_at: 确认时间
        is_final: 是否最终确认
    }
```

### 4.2 核心接口设计
```mermaid
sequenceDiagram
    participant User
    participant API
    participant DB

    User->>API: 上传设计稿
    API->>DB: 创建DESIGN_DRAFT记录
    DB-->>API: 返回设计稿ID
    API-->>User: 返回上传结果

    User->>API: 审核设计稿
    API->>DB: 更新DESIGN_DRAFT状态为已发布
    DB-->>API: 返回操作结果
    API-->>User: 返回审核结果

    User->>API: 提交修改意见
    API->>DB: 创建COMMENT记录
    DB-->>API: 返回意见ID
    API-->>User: 返回提交结果

    User->>API: 确认版本
    API->>DB: 创建CONFIRMATION记录
    DB-->>API: 返回确认ID
    API-->>User: 返回确认结果
```

## 五、主要实施任务
### 5.1 核心功能模块
1. **用户认证模块**
   - 实现角色权限验证
   - 项目成员绑定与访问控制
   - 撤销访问权限管理

2. **项目管理模块**
   - 项目创建与复制功能
   - 指定客户确认人
   - 项目成员管理

3. **设计稿管理模块**
   - 多文件格式支持（图片/PDF）
   - 版本控制与发布流程
   - 历史版本回溯

4. **意见管理模块**
   - 意见提交与绑定
   - 意见处理与状态跟踪
   - 意见与版本的强关联

5. **确认流程模块**
   - 确认状态记录
   - 修改申请流程
   - 确认状态继承控制

### 5.2 非功能需求
- **数据安全**：确保撤销访问后已下载文件的可追溯性
- **性能要求**：支持并发上传和意见提交
- **审计追溯**：完整记录所有操作日志
