# 设计稿送审与客户确认工具设计方案（实验阶段）  

---

## 一、业务理解  
**核心需求**：  
1. **角色分工**：  
   - **设计师**：上传设计稿并维护版本；  
   - **项目负责人**：审核设计稿并发布版本；  
   - **客户**：查看已发布版本，提交修改意见或确认版本。  
2. **流程闭环**：  
   - 设计稿 → 审核 → 发布 → 客户确认/反馈 → 新版本迭代 → 历史版本与意见保留。  
3. **数据管理**：  
   - 每个设计稿可更新多版本，客户仅能查看已发布的版本；  
   - 修改意见必须绑定设计稿与版本，新版本发布后旧版本与旧意见保留；  
   - 旧版本的确认状态不继承至新版本。  

---

## 二、规则与未知  
### 已知规则  
- **客户权限**：  
  - 仅能查看“已发布版本”，无法访问草稿或未发布版本；  
  - 提交的修改意见必须关联具体设计稿和版本；  
  - 旧版本的确认状态独立于新版本。  
- **流程控制**：  
  - 审核通过即自动发布；  
  - 新版本发布后，旧版本变为只读状态，但历史数据保留；  
  - 客户确认后如需修改，需客户提交申请，负责人接受后开启新流程，原确认状态保留。  
- **数据保留**：  
  - 所有版本、意见、确认记录均需完整存档；  
  - 意见处理需记录负责人是否采纳或说明原因。  

### 未知问题（待确认）  
1. **客户修改申请流程**：  
   - 客户提交修改申请后，是否需要负责人重新审核？  
   - 新版本是否需要重新走审核流程？  
2. **多客户协作**：  
   - 项目中存在多个客户时，如何管理不同客户的确认权限？  
3. **版本管理**：  
   - 是否支持版本比较功能（如对比新旧版本差异）？  
4. **通知机制**：  
   - 客户确认后是否需要通知负责人？  
   - 客户提交意见后是否需要通知负责人？  

---

## 三、关键状态及权限  
### 角色权限  
| 角色       | 权限描述                                                                 |
|------------|--------------------------------------------------------------------------|
| **设计师** | 上传设计稿、更新版本、查看历史版本（含未发布）                         |
| **负责人** | 审核设计稿、发布版本、处理客户意见、查看所有版本（含未发布）           |
| **客户**   | 查看已发布版本、提交修改意见、确认版本（仅对当前发布版本有效）         |

### 状态定义  
| 实体       | 状态类型                    | 说明                                                                 |
|------------|-----------------------------|----------------------------------------------------------------------|
| **设计稿** | 草稿、已审核、已发布       | 草稿需负责人审核后变为已审核，发布后客户可见                         |
| **版本**   | 当前发布、历史版本          | 当前发布版本为最新，历史版本仅可查看，不可修改                      |
| **意见**   | 待处理、已处理、已确认     | 意见仅对最新发布版本开放，处理状态需记录负责人操作                   |
| **确认**   | 未确认、已确认（仅对当前版本有效） | 旧版本的确认状态不继承，需单独记录                                  |

## 四、数据与接口设计  
### 数据结构（核心表）  
1. **用户表**：  
   - 用户ID、角色（设计师/负责人/客户）、所属项目、权限范围。  
2. **项目表**：  
   - 项目ID、项目名称、负责人ID、客户ID（可多对多）。  
3. **设计稿表**：  
   - 设计稿ID、项目ID、上传人ID、状态（草稿/已审核/已发布）。  
4. **版本表**：  
   - 版本ID、设计稿ID、文件路径（PDF/图片）、版本号、发布时间、状态（当前/历史）。  
5. **意见表**：  
   - 意见ID、版本ID、客户ID、内容、关联PDF页码、状态（待处理/已处理/已确认）、处理人ID、处理时间。  
6. **确认记录表**：  
   - 确认ID、版本ID、客户ID、确认时间、确认人ID。  

### 接口设计（RESTful API）  
1. **上传设计稿**：  
   - `POST /api/designs`  
   - 参数：项目ID、文件（PDF/图片）、设计稿名称。  
2. **审核设计稿**：  
   - `POST /api/designs/{designId}/approve`  
   - 参数：负责人ID、审核结果（通过/驳回）。  
3. **发布版本**：  
   - `POST /api/versions/{versionId}/publish`  
   - 参数：负责人ID。  
4. **提交意见**：  
   - `POST /api/versions/{versionId}/feedback`  
   - 参数：客户ID、内容、关联PDF页码。  
5. **处理意见**：  
   - `POST /api/feedbacks/{feedbackId}/process`  
   - 参数：负责人ID、处理状态（已处理/已确认）、处理说明。  
6. **确认版本**：  
   - `POST /api/versions/{versionId}/confirm`  
   - 参数：客户ID。

## 五、实施任务  
1. **前端开发**：  
   - 设计师上传界面（支持拖拽、文件类型校验）；  
   - 负责人审核与发布界面（可查看历史版本）；  
   - 客户查看版本界面（仅显示已发布版本）；  
   - 意见提交与确认界面（绑定设计稿和版本）。  
2. **后端开发**：  
   - 文件存储与版本管理逻辑（支持多版本上传）；  
   - 审核与发布流程控制；  
   - 意见处理与确认状态同步；  
   - 权限验证与状态校验（如客户仅可操作已发布版本）。  
3. **数据管理**：  
   - 历史版本与意见的持久化存储；  
   - 状态变更日志记录（如版本发布、意见处理）。  
4. **通知机制**（待确认）：  
   - 是否需要集成消息推送（如客户确认后通知负责人？）。

## 六、可验证验收场景  
1. **设计稿上传与审核**：  
   - 设计师上传设计稿 → 负责人审核通过 → 设计稿状态变为“已审核”。  
2. **版本发布**：  
   - 负责人发布版本 → 旧版本变为“历史版本”，新版本为“当前发布”。  
3. **客户查看与意见提交**：  
   - 客户仅能查看已发布版本 → 提交意见绑定设计稿和版本 → 意见状态为“待处理”。  
4. **意见处理与确认**：  
   - 负责人处理意见（标记已处理/已确认） → 客户确认版本 → 确认状态仅对当前版本有效。  
5. **历史数据保留**：  
   - 新版本发布后，旧版本与旧意见保留 → 旧版本的确认状态与新版本独立。

## 七、产品与技术自检  
### 产品自检  
- **覆盖需求**：  
  - 是否支持多版本、客户仅查看已发布版本、意见绑定设计稿与版本？  
  - 是否保留历史版本与旧意见？  
- **边界条件**：  
  - 客户提交意见后未处理，是否允许确认版本？  
  - 项目负责人撤销客户访问权限后，客户是否仍可查看已下载的副本？  

### 技术自检  
- **权限控制**：  
  - 角色权限是否通过中间件或数据库字段校验？  
- **状态一致性**：  
  - 版本发布后，旧版本状态是否正确更新？  
- **数据冗余**：  
  - 是否避免重复存储设计稿与版本文件？

### 待确认问题

   - 项目中多个客户如何管理确认权限？  
3. **通知机制**：  
   - 是否需要集成消息推送或邮件通知？
