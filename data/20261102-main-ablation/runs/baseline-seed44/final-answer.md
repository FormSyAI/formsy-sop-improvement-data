# 设计稿送审与客户确认工具 - 初始阶段设计方案

## 一、业务理解
工具需支持以下核心流程：
- **设计稿生命周期**：设计师上传→负责人审核→发布→客户确认/修改→新版本循环
- **版本管理**：每个设计稿可维护多个版本，新版本发布后保留历史版本
- **协作机制**：客户只能查看已发布版本，但可对当前版本提交修改意见
- **确认机制**：客户确认需基于最新发布版本，旧版本确认状态不继承

## 二、规则与未知
### 已知规则
1. **权限控制**  
   - 客户仅能访问自己参与项目的已发布版本  
   - 负责人可复制项目入口，但不自动通知  
   - 客户确认人可代表客户提交意见，其他客户可提意见  

2. **版本与确认逻辑**  
   - 新版本发布时，旧版本变为只读状态  
   - 意见仅关联当前发布版本，历史版本意见保留但不可操作  
   - 客户确认后需通过"重新修改申请"开启新流程，原确认状态保留  

3. **流程约束**  
   - 负责人审核通过即自动发布  
   - 意见需先处理才能允许确认  
   - 仅支持文字意见，可关联PDF页码  

### 未知问题（待确认）
1. **客户确认后的版本修改流程**  
   - 是否需要强制客户提交"重新修改申请"？  
   - 负责人接受申请后，如何标记新版本与原确认状态的关联？  

2. **项目成员权限边界**  
   - 负责人可自审并记录上传人和审核人，是否允许其他成员参与审核？  
   - 客户成员能否查看历史版本意见？  

3. **数据保留与撤销**  
   - 撤销访问权限后，已下载的文件是否保留？  
   - 历史版本的确认记录是否允许被修改？  

4. **多版本协作**  
   - 项目内多个设计稿的版本是否独立管理？  
   - 客户能否跨设计稿比较版本差异？  

## 三、关键状态及权限
| 角色       | 权限说明                                                                 |
|------------|--------------------------------------------------------------------------|
| **设计师** | 上传/更新设计稿，查看所有版本（含未发布）                                |
| **负责人** | 审核设计稿，发布版本，处理客户意见，复制项目入口                          |
| **客户**   | 查看已发布版本，提交修改意见，确认版本（仅限当前发布版）                  |
| **客户确认人** | 代表客户提交意见，确认版本，可查看所有客户成员提交的意见               |

| 状态       | 说明                                                                 |
|------------|----------------------------------------------------------------------|
| **设计稿状态** | 草稿（仅设计师可见）、已审核（负责人可见）、已发布（客户可见）         |
| **版本状态**   | 当前版本（可操作）、历史版本（只读）                                   |
| **意见状态**   | 待处理（负责人需处理）、已处理（负责人标记）、已确认（客户确认）       |
| **确认状态**   | 未确认（默认）、已确认（仅当前版本有效）、后续修改（新版本开启后状态） |

## 四、数据与接口设计
### 数据模型
1. **用户表**  
   - 用户ID、角色、项目成员关系、访问权限状态  

2. **项目表**  
   - 项目ID、负责人ID、客户确认人ID、项目成员列表  

3. **设计稿表**  
   - 设计稿ID、项目ID、设计师ID、标题、状态（草稿/已审核/已发布）  

4. **版本表**  
   - 版本ID、设计稿ID、文件路径（PDF/图片）、发布状态（当前/历史）、发布时间  

5. **意见表**  
   - 意见ID、版本ID、客户ID、内容、PDF页码、状态（待处理/已处理/已确认）  

6. **确认记录表**  
   - 确认ID、版本ID、客户ID、确认时间、备注（如"后续修改"标记）  

### 核心接口
1. **设计稿上传接口**  
   - 输入：设计稿信息、文件（PDF/图片）  
   - 输出：设计稿ID、状态（草稿）  

2. **版本发布接口**  
   - 输入：设计稿ID、版本内容  
   - 输出：版本ID、状态（当前）  

3. **意见提交接口**  
   - 输入：版本ID、客户ID、内容、PDF页码  
   - 输出：意见ID、状态（待处理）  

4. **确认操作接口**  
   - 输入：版本ID、客户ID、确认状态（确认/后续修改）  
   - 输出：确认记录、状态更新  

5. **项目复制接口**  
   - 输入：项目ID、目标用户ID  
   - 输出：新项目ID、复制成功状态  

## 五、主要实施任务
1. **权限系统开发**  
   - 实现基于角色和项目的访问控制（RBAC）  
   - 支持动态绑定/撤销项目成员权限  

2. **版本管理模块**  
   - 支持多版本存储与状态切换  
   - 实现版本历史保留与只读控制  

3. **意见跟踪系统**  
   - 意见与版本强关联（外键约束）  
   - 状态流转记录（待处理→已处理→已确认）  

4. **确认流程管理**  
   - 确认操作绑定当前版本ID  
   - 实现"后续修改"标记与历史确认记录关联  

5. **客户视图控制**  
   - 前端按项目过滤已发布版本  
   - 拦截对非当前版本的确认操作  

6. **数据存储优化**  
   - 版本文件存储路径设计（如：`/projects/{pid}/designs/{did}/versions/{vid}/`）  
   - 历史数据归档策略（如：保留所有版本及意见）  

## 六、可验证的验收场景
| 场景编号 | 操作流程                                                                 | 预期结果                                                                 |
|----------|--------------------------------------------------------------------------|--------------------------------------------------------------------------|
| S1       | 客户查看非自己项目的版本                                                 | 系统显示"无权限访问"提示                                                 |
| S2       | 负责人发布新版本后，客户尝试确认旧版本                                   | 系统提示"仅最新版本可确认"                                               |
| S3       | 客户提交意见后，负责人未处理，客户尝试确认版本                           | 系统提示"需处理所有意见后才能确认"                                       |
| S4       | 客户确认后，设计师更新新版本，客户提交新意见                             | 新意见仅关联最新版本，旧意见保留但不可操作                               |
| S5       | 撤销客户访问权限后，客户尝试下载已保存的文件                             | 系统允许下载，但提示"该文件已下载，访问权限已撤销"                       |

## 七、产品与技术自检
### 产品层面
- ✅ 覆盖用户明确的流程需求（如意见关联版本、确认状态不继承）  
- ❓ 未明确客户确认后的修改流程细节（需后续确认）  
- ❓ 未明确多客户成员的权限边界（需确认是否允许多人提交意见）  

### 技术层面
- ✅ 版本状态与权限控制通过状态机+RBAC实现  
- ❓ 意见与版本的关联需通过外键约束确保数据一致性  
- ✅ 历史数据保留通过版本表+意见表字段实现

2. 客户成员能否查看其他成员提交的意见？  
3. 撤销访问权限后，是否需要限制已下载文件的二次分发？
