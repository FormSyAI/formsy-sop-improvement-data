# 技术文档 SOP

开发流程模式：由 `formsy-sop-workflow` / `flow context` 协调时，本模块提供内容规则与审查，不另设阶段或例行确认。沿已有任务授权推进；实质修订保存差异并复检，实际缺少用户决定或扩大授权才询问。下文文档确认字段仍只记录真实确认，不能用程序推进伪造。

把当前项目的产品承诺写成可以实施、判断完成和失败恢复的技术设计。可以独立生成部分草案、整理已有设计或评审指定模块，不要求先运行其余 Skill。上游缺失保留缺口，只阻塞真正依赖它的决定或执行。

## 先固定本次任务

读取 [共同约定](references/共同约定.md)，识别项目、当前阶段与修订、用户要生成/整理/评审的范围、有效需求/产品行为/验收及决定。沿用已有稳定 ID 与原文；候选技术、未知平台、假设及授权不足均显式标识。历史 FormSyHelper 例子的凭据、平台或分数目标不能自动套用新项目。

已有有效选择不重复询问；按共同约定集中展示本模块的已知首轮问题，每题独立作答，后期新发现或冲突逐题补问。用户仅要求技术草案或评审时，先完成不依赖答案的内容；写方案不授予实施、安装、部署或付费调用权限。

## 生成或整理

1. 将需求/行为/验收映射到设计，反查每个新增模块、依赖、权限和任务的来源。技术支持动作可以关联交付目的，不据此增加用户功能。
2. 按稳定责任、数据所有者和信任边界划模块；小项目允许同进程或合并实现，契约责任仍清楚。必要动作有主负责方，失败传播与依赖方向可说明。
3. 模块卡写清输入校验、成功语义、接口与状态、唯一写入方、错误责任及取消/重复/恢复。对关键接口核对提供方与调用方；“已接收”不能充当“已持久保存”。
4. 数据模型说明约束、提交边界、失败保留、生命周期和适用的迁移/删除/恢复。用关键真实用户路径走读正常与反例，状态图、数据写入及反馈互相一致。
5. 将未知分为事实查证、核心假设试验、用户取舍和环境/权限/预算阻塞。技术事实按授权使用对应版本的一手来源；必须在目标环境证明的假设有事先判定条件，实际未做就保留未验证。
6. 全局计划保留完整目标和依赖；临近任务细化为输入、进入条件、步骤、产出、断言、停止和恢复。前任务只承诺当前可验证的子断言，依赖后任务的完整行为留到集成任务并列真实前置。状态/名单重置不能解除历史批准形成的变更门槛。每项验收按适用平台设计操作与证据；缺环境不删除平台、不继承另一平台通过。
7. 完整设计先固定资产、数据流和信任边界，再按实际能力展开安全专项。将威胁 TH、控制 CTRL、MOD/API/DATA、测试与证据版本绑定；SEC01–SEC12 在交接使用 `CUSTOM:SEC01` 等，不改 TC 原编号。加密、凭据保存、桌面配置和更新策略按实际平台及有效决定设计；候选选型不称已实施，安全用例未运行不称控制有效。部分修订只复核实际影响范围，并说明未审阅部分。
8. 将临近实施的任务拆到执行者可按卡开始：固定输入/对象版本、允许改动、依赖/进入条件、每步操作与中间结果、产物、可观察完成断言和验证、停止/取消恢复；文件和命令未定位不编造。实现与对应验证同任务闭环，另保留集成和完整用户路径任务。重要未知拆成查证/待决定，不把受阻实施写成ready；用TASK01–TASK10复核，粒度不足继续拆，已满足时停止无意义分割。

使用 [技术模板](assets/technical-template.md)组织输出。可以裁剪确实不适用的章节并记录理由；不能用占位表、库名称或“待后续”掩盖关键缺口。性能阈值、额度和重试次数有来源或待决定，不填任意数字。

## 评审和基础自查

用 TC01–TC15 覆盖本次技术对象，记录适用性、对象版本、定位、L1 结构/L2 语义/L3 所需查证与证据。缺资料是未核查或不满足，不是不适用；未做所需试验不能把其余层的满足汇总成整项满足。

使用 [技术评审模板](assets/technical-review-template.md)逐条输出实际发现、影响任务和下一动作。文档冲突按当前内容复检；实际可行性失败按规定环境重测。修改建议、问题台账完备与问题已关闭分别报告，高分不解除阻塞。涉及需求、方案或权限实质改变时展示差异并回相应阶段确认。

## 交付与停止

交付技术正文、双向追踪、任务/测试设计、来源与未知、当前自查和执行条件；机器交接方需要时另附 JSON 并填写真实字段，普通文档用等价 Markdown。无运行记录时 `runtime_results=[]`，无真实阶段确认时不得生成 `verified`。

只在已授权范围和有效预算内查证或试验；关键前提失效、需要用户决定、取消或预算停止时保存修订、未解决项及恢复条件，继续独立部分。无工具时给设计与限制，不声称文件已保存或应用已跑通。
