### 3.2 模块划分原则

1. 按稳定责任、数据所有权、信任边界和变化原因划分；一个模块有可描述的主责任，必要动作有唯一的主负责方。
2. 业务规则与显示交互、持久化、外部服务和知识资料治理分出明确边界；它们可以在同一进程内实现，不要求多服务部署。
3. 拆分应降低耦合并使失败、验证和恢复可处理。过度通用、重复封装和没有当前用途的模块需说明理由；小项目可合并实现，但契约责任仍清楚。
4. 数据写入、状态推进和错误处置明确由谁拥有；调用方不能绕过所有者直接修改数据或猜测成功。
5. 依赖方向避免循环；确需回调或事件时说明事件所有者、顺序、重复与失败处理，不能用“异步”隐藏一致性问题。
6. 共享支持模块通过接口供产品设计、技术设计和自检使用。知识库独立治理来源/版本/采用/范围；产品规则与阶段决定不由检索模块生成或改写。

**必要满足条件：** 模块全集与需求/数据流一致；每个模块完成第 4 节卡片；无责任空洞或相互冲突；划分粒度与风险有理由，模块依赖图可复核。

## 4. 每模块技术设计卡

每个模块复制一张卡。跨模块共用的大表可以通过稳定 ID 引用；不能只填“见架构图”。细节应足以确定输入处理、状态变化、数据读写、调用顺序、失败反馈及对应断言；深度按责任和风险裁剪，不按统一字数凑齐。

### 模块［模块 ID / 名称］填写卡

| 字段 | 项目必须填写的内容 |
| --- | --- |
| 来源与责任目的 | 关联需求、产品行为/功能、验收及交付目的 ID 与版本 |
| 主责任与边界 | 负责的具体动作、不承担的动作、调用方可依赖的保证 |
| 提供者与使用者 | 所在进程/运行环境、调用模块、真实用户路径中的位置 |
| 输入 | 类型、必填/可空、值域、大小/格式、版本、来源与校验失败结果 |
| 输出 | 结果类型、成功语义、部分结果标识、用户可见反馈与返回时机 |
| 接口 | 提供/调用接口 ID、同步/异步方式、调用顺序与契约版本 |
| 状态与生命周期 | 初始、运行、等待、完成、失败、取消和恢复状态；进入/退出条件；不适用状态的理由 |
| 数据所有权 | 自有/读取数据 ID、存储位置、唯一写入方、一致性与保留/删除规则 |
| 权限与信任 | 主体、项目/资料范围、调用校验、凭据句柄、外发或副作用范围 |
| 正常处理 | 关键输入到输出的步骤、规则、提交边界和关联场景 ID |
| 错误与部分失败 | 错误码、可见反馈、由谁处置、原数据/中间结果保留、下游影响 |
| 取消与重复 | 可取消点、已提交时的结果、重复请求识别、幂等范围及结果不明处理 |
| 恢复与退出 | 检查点、恢复前提、重授权/版本校验、重启/退出顺序、失败后的出口 |
| 依赖与配置 | 库/工具/服务版本、上下游前提、配置项、默认值来源及生效时机 |
| 资源与性能约束 | 时间/容量/内存/并发等必要约束、单位、数据规模、阈值来源与测量方法；无依据时待决定/待测 |
| 可行性依据 | 一手来源/版本/位置、支持的结论与限制；假设/试验 ID、实际证据状态 |
| 决策与权衡 | 候选方案、采用理由、代价、风险、重访条件、有效用户决定 |
| 实施任务 | 任务 ID、进入条件、依赖、产出及允许执行范围 |
| 验收映射 | 正常/反例/故障断言、验收与测试 ID、适用平台、证据取得方式 |
| 未决与阻塞 | 缺口、影响任务、下一动作、责任及关闭/恢复条件 |

持久化策略必须说明什么时候可以向用户报告成功，以及中断后保留什么。备份须有恢复方法；写出备份计划不表示备份可恢复。删除分别明确停止后续使用、删除受控对象、派生物清理、历史引用和远端已发送副本的边界。

**必要满足条件：** 类型与关联可复核；正常和失败读写与场景一致；所需数据保留/恢复不靠猜测；迁移和回退与交付范围一致；关键存储假设有适用资料或所需实际试验。
