# 设计稿送审与客户确认工具方案

## 一、业务理解
本工具服务于设计协作流程，涉及三类角色：
1. **设计师**：上传设计稿（支持图片/PDF）
2. **项目负责人**：审核设计稿并发布
3. **客户**：查看已发布版本、提交修改意见、确认最终版本

核心流程包含：
- 设计稿版本管理（多稿/多版本）
- 审核发布流程（自动触发）
- 意见处理流程（先处理再确认）
- 版本继承与隔离（新版本不影响旧版本状态）

## 二、规则与未知
### 已确认规则
1. **版本继承机制**
   - 新版本发布后旧版本只读
   - 旧版本确认状态不继承
   - 意见/确认仅对最新版本开放

2. **权限边界**
   - 客户仅可见本项目已发布版本
   - 意见必须关联设计稿+版本
   - 客户确认人特殊权限（其他客户只能提意见）

3. **流程约束**
   - 审核通过即自动发布
   - 修改需客户申请+负责人同意
   - 先处理意见再允许确认
   - 撤销访问不收回已下载副本

### 待确认问题
1. **多设计稿管理**
   - 是否需要为不同设计稿设置独立版本线？
   - 如何处理跨设计稿的版本关联？

2. **意见处理机制**
   - 负责人标记已处理的判定标准？
   - 未采纳意见的处理流程？

3. **版本追溯**
   - 如何实现"旧版本确认不等同新版本确认"的技术实现？
   - 历史版本的确认状态如何存储？

## 三、关键状态及权限
### 用户状态机
| 角色       | 可操作状态                         | 权限边界                             |
|------------|------------------------------------|--------------------------------------|
| 设计师     | 上传/更新设计稿                   | 仅限本项目设计稿                     |
| 负责人     | 审核/发布/自审                   | 全项目权限，可操作所有版本           |
| 客户确认人 | 确认版本                          | 仅限最新发布版本                     |
| 其他客户   | 提交意见                          | 仅限最新发布版本                     |

### 版本状态机
| 状态       | 触发条件                         | 后续状态                          |
|------------|----------------------------------|-----------------------------------|
| 草稿       | 设计师上传                       | 待审核/已发布                     |
| 待审核     | 负责人未处理                     | 已发布/已驳回                     |
| 已发布     | 审核通过                         | 只读/新版本发布                   |
| 已驳回     | 负责人驳回                       | 草稿/新版本发布                   |

## 四、数据与接口
### 核心数据模型
```json
{
  "project": {
    "id": "string",
    "name": "string",
    "client_confirmer": "user_id"
  },
  "design_draft": {
    "id": "string",
    "project_id": "string",
    "versions": ["version_id"] // 版本数组
  },
  "version": {
    "id": "string",
    "draft_id": "string",
    "status": "draft/published/archived",
    "created_at": "datetime",
    "confirmed_at": "datetime",
    "confirmed_by": "user_id"
  },
  "comment": {
    "id": "string",
    "version_id": "string",
    "user_id": "string",
    "content": "string",
    "page": "int",
    "status": "pending/processed"
  }
}
```

### 关键接口
1. **设计稿管理**
   - `POST /api/drafts`：上传新设计稿
   - `GET /api/drafts/{id}`：获取设计稿及版本列表

2. **版本控制**
   - `POST /api/versions/{id}/publish`：发布版本
   - `GET /api/versions/{id}/history`：获取版本历史

3. **意见管理**
   - `POST /api/comments`：提交修改意见
   - `PATCH /api/comments/{id}/process`：处理意见

4. **确认管理**
   - `POST /api/versions/{id}/confirm`：确认版本
   - `GET /api/versions/{id}/confirmations`：获取确认记录

## 五、实施任务
### 核心功能模块
1. **权限管理系统**
   - 实现用户-项目-角色绑定
   - 动态权限验证（基于RBAC模型）
   - 访问控制列表(ACL)管理

2. **版本控制系统**
   - 实现多设计稿的版本树管理
   - 版本状态变更日志记录
   - 版本隔离与继承机制

3. **意见处理系统**
   - 意见-版本关联管理
   - 处理状态跟踪
   - 意见处理日志记录

4. **确认流程系统**
   - 确认状态验证（仅限最新版本）
   - 确认历史记录
   - 修改申请流程管理

### 非功能需求
1. **数据安全**
   - 文件存储加密
   - 访问日志记录
   - 撤销访问后下载副本不可追溯

2. **性能要求**
   - 支持千级项目并发
   - 版本检索响应时间<500ms
   - 文件上传吞吐量≥10MB/s

## 六、可验证验收场景
### 场景1：基础流程验证
1. 设计师上传设计稿A（v1.0）
2. 负责人审核通过并发布
3. 客户查看v1.0并提交意见
4. 负责人处理意见后确认v1.0
5. 设计师更新为v1.1
6. 验证：v1.0确认状态不继承至v1.1

### 场景2：多版本验证
1. 创建项目P1，指定客户确认人C1
2. 设计师上传设计稿A（v1.0）和B（v1.0）
3. 客户C1查看P1所有已发布版本
4. 客户C2提交意见到设计稿A的v1.0
5. 验证：意见仅关联到指定设计稿和版本

### 场景3：修改流程验证
1. 客户确认v1.0后提交修改申请
2. 负责人接受申请生成v1.1
3. 验证：v1.0确认状态保留并标记为"后续修改"
