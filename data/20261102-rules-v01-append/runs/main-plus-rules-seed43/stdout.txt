# 设计稿送审与客户确认工具设计方案

## 一、业务理解

本工具旨在为设计工作流提供一个可追溯的线上审批流程，包含以下核心业务场景：
1. 设计师上传设计稿（支持图片和PDF）
2. 项目负责人审核设计稿并发布
3. 客户查看已发布的版本并提出修改意见
4. 设计师根据意见修改并上传新版本
5. 客户确认最终版本
6. 版本历史和意见记录的完整保留

## 二、规则与未知

### 已确认规则：
1. 身份系统：需要登录，支持电脑和手机访问
2. 权限管理：客户只能查看自己项目内已发布的版本
3. 版本管理：每份设计稿可更新多个版本
4. 意见关联：修改意见必须关联具体设计稿及版本
5. 版本保留：新版本发布后，旧版本与旧意见保留
6. 确认继承：旧版本的确认不能直接算作新版本已确认
7. 修改流程：客户确认后需要修改时，需提交重新修改申请
8. 意见处理：负责人需标记已处理或说明不采纳
9. 文件管理：支持文字意见，可选PDF页码，允许下载
10. 撤销访问：不能收回已下载副本
11. 通知方式：负责人需手动通知，暂不自动发消息
12. 自审功能：负责人可自审并记录上传人和审核人

### 未知问题：
1. 需要明确项目成员的权限边界（设计师、负责人、客户）
2. 需要确认设计稿的文件类型和大小限制
3. 需要确定是否支持多项目管理
4. 需要确认客户确认后是否允许设计稿继续修改
5. 需要明确意见处理的时间限制
6. 需要确定是否支持多个客户确认人
7. 需要确认文件存储和访问权限的实现方式
8. 需要确定项目负责人审核的具体标准

## 三、关键状态及权限

| 状态 | 权限 | 描述 |
|------|------|------|
| 设计稿上传 | 设计师 | 上传图片或PDF文件 |
| 设计稿待审核 | 项目负责人 | 审核设计稿并决定是否发布 |
| 设计稿已发布 | 所有项目成员 | 可查看已发布的版本 |
| 意见提交 | 客户 | 提交修改意见（需关联设计稿和版本） |
| 意见已处理 | 项目负责人 | 标记意见已处理或说明不采纳 |
| 版本更新 | 设计师 | 根据意见修改并上传新版本 |
| 版本确认 | 客户 | 确认最终版本 |
| 修改申请 | 客户 | 提交修改申请（需关联设计稿和版本） |
| 修改确认 | 项目负责人 | 接受修改申请并开启新一轮审批 |

## 四、数据与接口设计

### 数据模型

1. **项目（Project）**
   - ID
   - 名称
   - 创建时间
   - 项目成员（设计师、负责人、客户）
   - 客户确认人

2. **设计稿（DesignDraft）**
   - ID
   - 项目ID
   - 上传人
   - 上传时间
   - 文件类型（图片/PDF）
   - 文件大小
   - 文件路径
   - 版本号
   - 状态（待审核/已发布）

3. **版本（Version）**
   - ID
   - 设计稿ID
   - 版本号
   - 上传时间
   - 文件路径
   - 状态（已发布/已确认）

4. **意见（Comment）**
   - ID
   - 项目ID
   - 设计稿ID
   - 版本号
   - 提交人
   - 提交时间
   - 内容
   - PDF页码（可选）
   - 状态（待处理/已处理）
   - 处理人
   - 处理时间
   - 处理结果（已采纳/不采纳）

5. **确认记录（Confirmation）**
   - ID
   - 项目ID
   - 设计稿ID
   - 版本号
   - 确认人
   - 确认时间
   - 状态（确认/修改申请/已修改确认）

### 接口设计

1. **设计稿上传接口**
   - POST /design-draft/upload
   - 请求参数：项目ID、文件类型、文件内容
   - 响应：设计稿ID、版本号

2. **设计稿审核接口**
   - POST /design-draft/approve
   - 请求参数：设计稿ID、审核结果
   - 响应：审核状态

3. **版本发布接口**
   - POST /version/publish
   - 请求参数：设计稿ID、版本号
   - 响应：版本状态

4. **意见提交接口**
   - POST /comment/submit
   - 请求参数：项目ID、设计稿ID、版本号、内容、PDF页码
   - 响应：意见ID

5. **意见处理接口**
   - POST /comment/process
   - 请求参数：意见ID、处理结果
   - 响应：处理状态

6. **版本确认接口**
   - POST /version/confirm
   - 请求参数：设计稿ID、版本号
   - 响应：确认状态

7. **修改申请接口**
   - POST /version/request-modification
   - 请求参数：设计稿ID、版本号
   - 响应：修改申请状态

8. **修改确认接口**
   - POST /version/confirm-modification
   - 请求参数：设计稿ID、版本号
   - 响应：修改确认状态

## 五、实施任务

1. 实现身份认证和项目成员管理功能
2. 开发设计稿上传和版本管理模块
3. 实现项目负责人审核和发布流程
4. 开发客户意见提交和处理模块
5. 实现版本确认和修改申请流程
6. 实现文件存储和访问权限管理
7. 开发项目成员的查看和操作权限控制
8. 实现意见处理状态跟踪和记录
9. 开发版本历史和意见记录的展示功能
10. 实现项目负责人的通知和自审功能

## 六、可验证的验收场景

1. **设计稿上传验证**
   - 设计师上传设计稿后，系统应正确记录设计稿信息
   - 系统应显示设计稿状态为"待审核"

2. **设计稿审核验证**
   - 项目负责人审核设计稿后，系统应更新设计稿状态为"已发布"
   - 系统应记录审核人和审核时间

3. **意见提交验证**
   - 客户提交意见后，系统应正确记录意见内容、关联设计稿和版本
   - 系统应显示意见状态为"待处理"

4. **意见处理验证**
   - 项目负责人处理意见后，系统应更新意见状态为"已处理"
   - 系统应记录处理人、处理时间和处理结果

5. **版本确认验证**
   - 客户确认版本后，系统应记录确认人和确认时间
   - 系统应显示版本状态为"已确认"

6. **修改申请验证**
   - 客户提交修改申请后，系统应记录申请信息
   - 系统应显示修改申请状态为"待处理"

7. **修改确认验证**
   - 项目负责人接受修改申请后，系统应更新版本状态
   - 系统应记录修改确认信息

8. **版本历史验证**
   - 系统应完整展示设计稿的所有版本历史
   - 系统应显示每个版本的上传人、上传时间和状态

9. **意见记录验证**
   - 系统应完整展示所有关联设计稿和版本的意见记录
   - 系统应显示每条意见的提交人、提交时间和处理状态

10. **权限验证**
    - 客户只能查看自己项目内已发布的版本
    - 项目负责人应能查看所有项目成员的操作记录
    - 设计师应只能查看自己上传的设计稿
