# 事实卡 + 机器门禁 + 定向修正消融报告 v0.3

日期：2026-11-02。案例：设计稿送审与客户确认工具，第一阶段。

## 结论

这轮验证了三层流程的价值，但也暴露出一个关键事实：**短事实卡本身不稳定，机器门禁是必要层，但一次定向修正不能保证全部通过。**

| 处理组 | 初始门禁通过 | 定向修正后门禁通过 |
|---|---:|---:|
| FactCard | 1/3 | 1/3 |
| MainSOP 既有输出 | 0/3 | 1/3 |

修正前后按机器门禁事实覆盖率看：

| 运行 | 初始缺失事实数 | 修正后缺失事实数 | 变化 |
|---|---:|---:|---:|
| fact-card-seed42 | 0 | 0 | 0 |
| fact-card-seed43 | 5 | 3 | -2 |
| fact-card-seed44 | 6 | 5 | -1 |
| mainsop-seed42 | 3 | 2 | -1 |
| mainsop-seed43 | 1 | 0 | -1 |
| mainsop-seed44 | 5 | 0 | -5 |

结论不是“短事实卡失败”，而是：

> 事实卡能把 seed42 做到全绿，但无法稳定约束所有 seed；机器门禁能把失败点定位成可修正输入，但一次修正只对部分样本有效。

## 实验设计

这轮不是继续比较长 SOP 的插入位置，而是拆成三层：

1. **生成前短事实卡**：只注入 10 条已确认事实、禁用扩展能力和技术边界，prompt 仅 906 tokens。
2. **生成后机器门禁**：用固定正则检查 10 条事实承接和禁用扩展词。
3. **一次定向修正**：把门禁失败项、原始输出、事实卡和修正要求一起给模型，只做一次修正，不重跑完整 SOP。

对照组使用既有 MainSOP 输出，不再重新推理：

- MainSOP 初始输出先过同一机器门禁。
- 失败项用同样的定向修正 prompt 修正一次。

## 机器门禁

检查 10 条事实：

- F01 审核通过即自动发布。
- F02 新版本发布后，旧版本只读。
- F03 意见和确认仅对最新发布版开放。
- F04 历史完整保留。
- F05 客户只能查看自己项目内已发布版本。
- F06 修改意见必须绑定具体设计稿及版本。
- F07 旧版本确认不继承到新版本。
- F08 先处理意见，才允许客户确认人确认。
- F09 每项目指定一名客户确认人；其他客户可提意见，不能确认。
- F10 撤销访问不能收回已下载副本。

同时检查禁用扩展词：

管理员、通知模块、自动通知、云存储、云端存储、归档、备份恢复、数据备份、邀请链接、链接生成、版本对比、批量上传、匿名意见、大文件上传、多语言。

门禁规则：

- 明确位于“候选建议，不进入本期范围”中的扩展能力不计为范围违规。
- 正文中出现禁用扩展词则记为失败。
- “不归档，仅保留历史记录”这类否定表述不计为归档违规。

需要说明：门禁脚本在实验过程中修正过三次正则误报，包括 F07、F08、F10 和候选建议边界。全部修正记录保留在 `gate-v2.json`、`gate-v3.json`、`gate-v4.json` 中。最终结论只使用 `gate-v4.json`。

## FactCard 初始输出

Prompt tokens：906。

| 运行 | 门禁缺失事实 | 范围违规 | 门禁 |
|---|---|---|---|
| seed42 | 无 | 无 | 通过 |
| seed43 | F03、F05、F06、F09、F10 | 云存储、归档 | 失败 |
| seed44 | F01、F03、F05、F07、F09、F10 | 无 | 失败 |

seed42 是事实卡的最佳样本：10 项事实全部通过，且没有范围违规。seed43 和 seed44 虽然有 906-token 事实卡，仍出现关键事实缺失和范围膨胀。

这说明短提示并不能稳定替代完整 SOP。它的优点是成本低、注意力集中、失败点可定位；缺点是模型仍可能只形式化复述事实卡，而没有把它们落到状态、接口、权限和验收中。

## MainSOP 既有输出门禁结果

| 运行 | 门禁缺失事实 | 范围违规 | 门禁 |
|---|---|---|---|
| seed42 | F08、F09、F10 | 无 | 失败 |
| seed43 | F04 | 自动通知、云存储 | 失败 |
| seed44 | F01、F02、F03、F07、F09 | 管理员、通知模块、数据备份、版本对比、批量上传 | 失败 |

这一步说明 MainSOP 的 8/8 人工事实评分和机器门禁并不等价。机器门禁更严格，尤其检查 F09 权限细分和 F10 下载副本。MainSOP seed42 虽然人工评审为 8/8、0 缺陷，但机器门禁仍发现其未明确“先处理意见”“唯一确认人”“下载副本”三项。

这不是人工评审错误，而是指标不同：

- 人工事实覆盖检查输出是否承接业务事实。
- 机器门禁检查是否能用固定证据定位到输出文本。

## 定向修正

每个失败输出只修正一次。修正 prompt 包含：

1. 原案例输入。
2. 原始输出。
3. 事实卡。
4. 机器门禁失败项。
5. 修正要求：
   - 不重问已确认事实。
   - 未确认能力不得进入实施任务、接口或数据模型。
   - 意见、确认、查看、下载、审核、发布必须绑定 version_id。
   - 审核通过和发布对外是一个业务动作。
   - 权限矩阵必须区分客户确认人和其他客户。

### FactCard 修正结果

| 运行 | 初始缺失 | 修正后缺失 | 范围违规 | 门禁 |
|---|---:|---:|---|---|
| seed42 | 0 | 0 | 无 | 通过 |
| seed43 | 5 | 3 | 云存储、版本对比 | 失败 |
| seed44 | 6 | 5 | 无 | 失败 |

seed43 减少了两个缺失事实，但仍缺项目隔离、唯一确认人和下载副本，且保留云存储、版本对比等未确认能力。seed44 只减少一个缺失事实，且新增 F01 自动发布缺失。

### MainSOP 修正结果

| 运行 | 初始缺失 | 修正后缺失 | 范围违规 | 门禁 |
|---|---:|---:|---|---|
| seed42 | 3 | 2 | 无 | 失败 |
| seed43 | 1 | 0 | 无 | 通过 |
| seed44 | 5 | 0 | 管理员、归档 | 失败 |

MainSOP seed43 修正后完全通过。seed44 的 5 个缺失事实全部修正，但仍保留管理员和归档等未确认能力。seed42 只修正了下载副本，仍缺“先处理意见”和“唯一确认人”。

## 关键发现

### 1. 短事实卡不等于硬约束

906-token 事实卡能显著降低成本，并让 seed42 全绿，但 seed43/44 仍失败。事实如果只作为文本列出，模型仍可能没有把它们落到权限矩阵、接口和验收里。

### 2. 机器门禁暴露了人工评分的盲区

MainSOP seed42 原人工评审为 8/8、0 缺陷，但机器门禁发现其缺 F08、F09、F10。这说明人工评审更容易把“上下文合理”当成“事实已显式承接”。

### 3. 一次定向修正能收敛，但不能保证收敛

修正收益最明显的是 MainSOP seed44：缺失事实从 5 个降到 0 个。但 FactCard seed43/44 仍不稳定。因此，修正轮次需要设置预算，不能无限重试。

### 4. 范围膨胀比事实缺失更难修正

seed44 的 5 个事实缺失全部被修正，但管理员和归档仍然保留。模型倾向于“补充要求”，但不擅长删除已出现的扩展能力。

### 5. MainSOP 输出更适合作为修正基底

MainSOP 既有输出经过一次修正后，有两个样本事实全绿，其中 seed43 完全通过门禁。FactCard 只有 seed42 全绿。完整 SOP 虽然生成时不稳定，但输出结构更完整，作为修正基底比短事实卡更有优势。

## 边界

1. 本实验仍只有一个案例、一个模型、3 个 seed。
2. 机器门禁是正则门禁，能定位缺失证据，但不能证明设计实现正确。
3. 一次修正不等于最终方案，只验证定向修正是否有收敛趋势。
4. MainSOP 对照组没有重新推理初始输出，而是复用前面正式实验的输出，因此只比较“相同初始输出 + 一次修正”的效果。
5. 门禁正则经过三次修正，最终报告只采用 gate-v4。

## 下一步建议

1. **使用 MainSOP 输出作为修正基底**，而不是用短事实卡直接生成最终稿。
2. **机器门禁先跑，失败项再修正**；不把完整 SOP 继续加长。
3. **范围膨胀需要删除型指令**：要求模型逐项列出“已移除的未确认能力”，而不是只要求“补充事实”。
4. **修正轮次固定为 2 轮**：第 1 轮补事实和接口边界，第 2 轮只删除范围膨胀。
5. **把 F08、F09、F10 设为 P0 门禁**：先处理意见、唯一确认人、下载副本是本案例最容易漏且业务风险最高的三条。
