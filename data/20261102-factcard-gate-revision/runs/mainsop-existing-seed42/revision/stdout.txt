# 设计稿送审与客户确认工具设计方案（修订版）

## 一、业务理解与规则说明

### 1. 核心业务流程
- **设计稿管理**：设计师上传设计稿（支持图片/PDF格式），每个设计稿可生成多个版本（V1/V2/V3...）
- **审核发布流程**：负责人审核设计稿，审核通过后自动发布，旧版本转为只读状态
- **客户确认流程**：客户只能查看已发布版本，可对最新版本提出修改意见或确认
- **版本迭代机制**：新版本发布后保留历史版本，客户确认状态不继承至新版本
- **修改申请机制**：客户确认后如需修改，需提交修改申请，负责人审批后开启新版本流程

### 2. 权限规则
| 角色       | 权限范围                          | 限制条件                          |
|------------|-----------------------------------|-----------------------------------|
| 设计师     | 上传设计稿、更新版本              | 仅限本项目成员                   |
| 负责人     | 审核设计稿、发布版本、处理意见    | 可查看所有版本和历史意见         |
| 客户       | 查看已发布版本、提出意见、确认    | 仅限本项目成员，无法访问草稿版本 |
| 客户确认人 | 确认版本                          | 每个项目仅一人，其他客户不可确认 |

## 二、关键状态与权限设计

### 1. 状态机设计
```mermaid
graph TD
    A[草稿状态] --> B[审核中]
    B --> C{审核通过?}
    C -->|是| D[已发布]
    C -->|否| E[未发布]
    D --> F[客户可查看]
    D --> G[可提交意见/确认]
    D --> H[可申请修改]
```

### 2. 数据隔离规则
- 客户仅能访问：
  - 本人所属项目的已发布版本
  - 与已发布版本相关的修改意见
- 旧版本数据保留机制：
  - 版本状态：只读（不可修改）
  - 意见状态：可查看但不可操作
  - 确认状态：保留历史记录但不继承

## 四、主要实施任务

### 1. 基础功能模块
- **用户权限系统**：实现角色权限控制（设计师/负责人/客户）
- **文件存储系统**：支持图片/PDF上传与版本管理
- **审核工作流**：设计稿审核流程与版本发布机制
- **意见管理模块**：客户意见提交、处理状态跟踪
- **确认状态管理**：客户确认记录与版本关联

### 2. 历史数据管理
- 版本历史快照：完整保留所有版本数据
- 操作日志记录：记录审核、发布、确认等关键操作
- 意见追溯系统：建立版本与意见的关联关系

### 3. 安全与合规
- 数据隔离：确保客户只能访问所属项目数据
- 审计追踪：记录所有关键操作（上传、审核、确认）
- 数据保留：永久保存历史版本和操作记录

## 五、可验证的验收场景

### 1. 基础功能验证
- [ ] 客户无法查看未发布的版本（测试场景：客户尝试访问草稿版本）
- [ ] 新版本发布后旧版本保持只读状态（测试场景：上传V2后验证V1的编辑权限）
- [ ] 意见必须关联具体版本（测试场景：尝试提交未关联版本的意见）
- [ ] 客户确认状态不继承到新版本（测试场景：确认V1后发布V2，验证V2的确认状态）
- [ ] 撤销访问后已下载副本仍可保留（测试场景：撤销访问后验证下载的副本是否可访问）

### 2. 流程完整性验证
- [ ] 客户确认后修改申请流程（测试场景：客户确认V1后提交修改申请，验证新版本生成流程）
- [ ] 意见处理状态跟踪（测试场景：提交意见后验证状态变更记录）
- [ ] 多版本并行处理（测试场景：同时存在V1/V2/V3时的权限控制）

### 3. 数据完整性验证
- [ ] 历史版本数据保留（测试场景：删除V1后验证数据是否仍可访问）
- [ ] 操作日志可追溯（测试场景：查询特定操作的审计记录）
- [ ] 意见与版本关联关系（测试场景：验证意见记录中的版本ID有效性）

## 六、待确认事项与建议

### 1. 待确认问题
1. 多负责人场景处理：当项目有多个负责人时，审核流程如何处理？
2. 意见处理优先级：当有多个未处理意见时，确认流程如何处理？
3. 版本比较功能：是否需要提供版本差异对比功能？
4. 修改申请审批：负责人审批修改申请的流程是否需要二次确认？

### 2. 暂定选择建议
1. **多负责人处理**：建议采用会签模式，需所有负责人确认后发布
2. **意见处理优先级**：建议按提交时间顺序处理，支持标记紧急/重要
3. **版本比较功能**：建议提供基础的版本差异对比功能
4. **修改申请审批**：建议采用负责人确认制，无需二次确认

## 七、实施风险点

1. **历史数据管理**：需要确保历史版本和操作记录的完整性和可追溯性
2. **权限控制复杂度**：需要精确控制不同角色对不同版本的访问权限
3. **状态机复杂度**：需要处理多个状态转换场景（审核/发布/确认/修改）
4. **数据隔离要求**：必须确保客户只能访问所属项目数据，防止数据泄露

本方案严格遵循用户需求，未做任何功能扩展假设。建议在实施前确认待确认事项，并进行完整的验收测试。 [end of text]
