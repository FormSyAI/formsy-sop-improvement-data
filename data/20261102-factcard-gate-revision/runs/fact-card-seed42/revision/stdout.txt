# 设计稿送审与客户确认工具：初始阶段完整设计（修订版）

## 一、业务理解与规则
### 已确认核心规则（F01~F10）
1. **版本控制**  
   - 设计稿支持多版本迭代，新版本发布后旧版本变为只读  
   - 旧版本与历史意见、确认记录必须永久保留  
   - 新版本的确认操作独立于旧版本确认状态（F07）  

2. **权限控制**  
   - 客户仅能访问本项目已发布的版本（F05）  
   - 意见提交与确认操作仅对最新版本开放（F03）  
   - 项目内仅指定1名客户确认人，其他客户仅可提意见（F09）  
   - 意见提交前需先处理（F08）  

3. **流程约束**  
   - 审核通过即自动发布（F01）  
   - 撤销访问不影响已下载副本（F10）  
   - 修改意见必须绑定具体设计稿及版本（F06）  

### 待确认问题（需后续澄清）
1. **客户确认后的修改流程**  
   - 用户提到"客户确认后需提交修改申请"，但未明确：  
     - 修改申请是否需要负责人审批？  
     - 新版本是否需要重新审核？  
     - 原确认状态如何与新版本关联？  

2. **历史数据存储边界**  
   - F04要求"历史完整保留"，但未明确：  
     - 是否需要版本历史快照？  
     - 旧版本的只读访问是否允许下载？  
     - 意见/确认记录是否与版本强绑定？  

3. **权限矩阵细节**  
   - F02要求"旧版本只读"，但未定义：  
     - 只读权限是否包含下载？  
     - 客户确认人对旧版本是否有特殊权限？

## 二、状态与权限设计
### 用户角色状态
| 角色         | 可操作状态                         | 权限限制                       |
|--------------|------------------------------------|--------------------------------|
| 设计师       | 上传设计稿、更新版本               | 无审核/确认权限               |
| 项目负责人   | 审核设计稿、发布版本               | 无客户确认权限                |
| 客户确认人   | 确认最新版本                       | 仅对本项目有确认权限          |
| 其他客户     | 提交意见、查看已发布版本           | 无确认权限，无修改权限        |

### 版本状态机
```plaintext
[草稿]  
  ┌───────────────┐  
  │ 审核通过       │  
  └───────┬───────┘  
          ↓  
[已发布]  
  ┌───────────────┐  
  │ 新版本发布     │  
  └───────┬───────┘  
          ↓  
[旧版本]（只读）  
```

## 三、数据模型与接口设计
### 数据实体
```mermaid
erDiagram
    PROJECT -->|< DESIGN_DRAFT : "包含"
    DESIGN_DRAFT -->|< VERSION : "包含多个版本"
    VERSION -->|< COMMENT : "关联意见"
    VERSION -->|< CONFIRMATION : "关联确认"
    PROJECT -->|< CUSTOMER : "客户成员"
    CUSTOMER -->|< CONFIRMER : "指定确认人"

    VERSION {
        version_id PK
        design_draft_id FK
        status VARCHAR(20)  // 草稿/已发布/旧版本
        is_deleted BOOLEAN
        uploaded_at DATETIME
    }

    COMMENT {
        comment_id PK
        version_id FK
        content TEXT
        page_number INT
        created_at DATETIME
        is_handled BOOLEAN
    }

    CONFIRMATION {
        confirmation_id PK
        version_id FK
        confirmor_id FK
        confirmed_at DATETIME
        remark TEXT
    }
```

### 关键接口清单
| 接口名称              | 路径                          | 方法 | 说明                           |
|-----------------------|-------------------------------|------|--------------------------------|
| 创建项目              | /api/project/create           | POST | 初始化项目并绑定客户成员       |
| 上传设计稿            | /api/design/upload            | POST | 上传文件并创建初始版本         |
| 审核并发布版本        | /api/version/approve          | POST | 审核通过后自动发布（F01）      |
| 提交修改意见          | /api/comment/create           | POST | 需绑定version_id（F06）        |
| 客户确认版本          | /api/confirmation/create      | POST | 仅对最新版本开放（F03）        |
| 查看版本列表          | /api/project/versions         | GET  | 仅返回已发布版本（F05）        |
| 查看历史记录          | /api/project/history          | GET  | 包含所有版本与操作记录（F04）  |

## 四、实施任务分解
### 核心开发任务
1. **版本控制模块**  
   - 实现版本状态机（草稿→已发布→旧版本）  
   - 旧版本只读逻辑（禁止修改、删除）  

2. **权限控制模块**  
   - 客户确认人身份绑定（项目级）  
   - 意见提交与确认的version_id校验  

3. **数据保留机制**  
   - 历史记录存储（版本、意见、确认记录）  
   - 旧版本数据不可变（仅可读）  

4. **流程校验逻辑**  
   - 意见处理前置校验（F08）  
   - 新版本确认不继承旧确认（F07）

## 五、可验证的验收场景
### 场景1：版本发布流程
- 前置条件：设计师上传v1设计稿，负责人审核通过  
- 操作：负责人调用`/api/version/approve`  
- 预期：v1变为已发布状态，旧版本（若存在）变为只读  

### 场景2：客户确认权限
- 前置条件：项目有客户A（非确认人）和客户B（确认人）  
- 操作：客户A尝试确认v1  
- 预期：系统返回403错误（F09）  

### 场景3：历史数据保留
- 操作：发布v2后查看历史记录  
- 预期：v1的确认记录仍可见，但无法修改（F07）
