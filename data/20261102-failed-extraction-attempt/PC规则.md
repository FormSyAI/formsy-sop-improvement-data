# 产品SOP自检方案：本模块相关部分

## 1. 为什么需要独立的产品自检

产品自检回答：这份 SOP 是否准确表达用户要解决的问题，能否说明用户如何完成任务，功能、交互、数据和验收是否一致，还有哪些产品取舍必须先决定？

技术自检回答：技术方案如何实现这些要求，模块、接口、数据和环境是否可行。两者以需求、功能和验收 ID 交接；分别保留产品问题和技术问题，不用技术方案合理替代产品目标合理。

现有规范已经包含产品检查，见 Q07/Q08/Q09/Q13/Q16/Q21〔原资料：sop-output-standard/references/质量检查表.md；未作为本模块运行依赖〕。缺口在于这些检查尚未展开为产品专属的适用规则、具体满足条件、证据、问题台账和复检过程。本文细化已有方向，不宣称产品检查从未存在。

### 1.1 各类结论分别记录

| 结论 | 回答什么 | 所需依据与限制 |
| --- | --- | --- |
| 产品文档检查 | 规定对象是否完整、一致、可理解、可交接 | 当前文档、规则、来源和分层核查记录；不等于真实产品已通过 |
| 技术文档检查 | 对应实现设计、交接和所需可行性是否就绪 | 使用独立技术规则及其所需查证／试验；不以产品文档分代替 |
| 产品主张得到支持 | 用户问题、任务或效果主张有哪些依据 | 原始表达、适用研究或真实观察；清楚标明样本、环境、限制和未验证假设 |
| 阶段用户确认 | 用户是否接受当前版本的目标、需求或规划 | 对应阶段和版本的有效用户决定；自检、资料和分数不能代替 |
| 实际产品验收 | 对应构建在目标环境能否完成正式条件 | 实际操作、文件、日志、截图及断言；文档、原型和单纯构建不能代替 |

私人使用的小工具可以根据使用者的明确要求形成设计，不强制市场调查。面向外部用户时，对“很多人需要”“能提高效率”“愿意付费”等主张要标明证据程度；PRD 字段齐全、作者自评和用户批准都不证明商业价值。

### 1.2 三层检查

| 层次 | 方法 | 可支持什么 | 不可推出什么 |
| --- | --- | --- | --- |
| L1 结构核查 | 按可重复规则查字段、占位、ID、引用、覆盖对象和版本 | 实际执行的结构规则满足或不满足 | 用户需要、流程可用、产品效果、试验完成 |
| L2 产品内容复核 | 按原始需求走读目标、任务、页面、功能、状态和验收；反向查越界；按适用性查外部事实 | 具体的行为一致性、缺口、冲突及依据范围内的设计判断 | 真实用户理解、全部场景可用、商业成立、用户批准 |
| L3 主张查证与真实研究／原型证据 | 针对事先明确的问题，记录实际访谈、观察、文档走读、原型任务或目标环境试验 | 在所述方法、样本和环境下取得的结果；不能扩大结论范围 | 最终产品全部通过、所有用户满意、其他平台通过 |

每条检查声明所需层次；正式资料可支持其明确说明的事实，不替代实际用户或原型试验。只有试验计划时记录“未执行”。模型提出用户画像、模拟用户或扮演评审，是建议与审查活动，不是实际用户研究。

检查状态：**满足 / 不满足 / 未核查 / 不适用＋理由**。真实研究或试验的观察、结果、限制独立记录；实际产品测试另记 **通过 / 失败 / 未验证 / 不适用＋理由**。三层未必都适用于每个对象，但所需层次尚未完成时不能把整项判满足。


## 2. 输入与输出对象

| 对象 | 最少内容 |
| --- | --- |
| 产品基线 | 项目、文档和规则版本；当前阶段；用户决定；使用者、范围、平台；原始资料定位和内容标识 |
| 用户与任务 | 已知用户和场景、要完成的任务、当前困难、目标结果；事实／建议／假设／未知分类 |
| 产品设计 | 范围和优先级、用户旅程、适用页面／入口、功能卡、状态规则、数据和权限行为 |
| 验收设计 | 需求和验收 ID、条件、环境、数据、操作、可观察断言、证据计划及平台适用性 |
| 检查清单 | PC01–PC15、对象集合、适用性、所需层次、满足条件及依据 |
| 研究或原型卡 | 问题与假设、方法、样本／环境、授权、事先判断口径、真实观察、结果及限制 |
| 问题台账 | 问题、定位、影响、严重程度、阻塞、处理者、下一动作、复检与历史 |
| 交接记录 | 产品对象→技术对象→任务→验收映射、冲突、待决定、当前阶段确认及影响 |

产品设计沿用现有 [功能设计卡和典型用户完整任务](<../assets/产品SOP模板.md>)，保留已有稳定 ID 和正式原文。技术映射使用 技术自检方案〔原资料：技术SOP自检研究/自检机制方案.md；未作为本模块运行依赖〕，不要求先写完代码才能核查产品文档。


## 3. 七步处理闭环

### 1）固定版本、对象和适用性

读取当前产品基线、原始资料、用户决定、平台和范围。固定需求、用户任务、功能、页面、状态、验收的对象清单及规则版本。无正式确认也可以核查草案，不能把草案结论变成已确认。

依据实际产品裁剪。例如无登录功能不要求设计登录页；没有外部付费服务不要求计费流程。范围不明确、资料缺失或环境不可用是待处理条件，不能为提高分数写“不适用”。

### 2）检查结构和引用

逐项检查必需字段、未填占位、重复编号、无效引用、来源身份、对象版本、必需需求及平台组合漏行。现阶段这些是检查规则方案，尚不能称应用已经自动执行了它们。

一个字段写了文字不表示内容满足。例如“失败时提示”没有说明提示和保留行为，应继续进入内容复核。

### 3）走读产品内容与完整任务

从用户任务起点开始，按正常和适用分支检查：入口→用户动作→系统反馈→状态和数据变化→最终结果或退出。逐条比较功能卡、页面、规则与验收；反向检查新增功能、权限、费用和数据外发是否有来源。

可安排另一位审阅者或另一轮复核，并保留异议和定位。同一模型重复自评不构成独立客观证据；有分歧时用原文、适用事实、真实观察或用户决定解决，不投票制造正确性。

### 4）把未知分流

| 未知 | 例子 | 下一动作 | 关闭依据 |
| --- | --- | --- | --- |
| 可查事实 | 目标平台的交互约束、外部服务支持和错误含义 | 查一手资料，记录版本和适用性 | 可定位依据支持所需事实，冲突得到解释 |
| 用户取舍 | 删除是否可撤销、自动覆盖还是另存、数据外发与费用 | 展示选项、后果和建议；逐个询问影响最大的事项 | 当前版本的有效用户决定 |
| 用户问题或效果假设 | 特定任务是否困难、用户能否理解、流程是否节省时间 | 根据影响设计适用的访谈、观察或原型任务；只执行已授权活动 | 实际记录和事先口径，明确样本与结论限制 |
| 技术可行性 | 目标平台能否按产品承诺运行、恢复数据 | 关联技术问题与验证卡 | 技术查证或所需实际试验结果，不能仅因写好设计关闭 |
| 环境／权限／预算阻塞 | 无目标环境、缺必要授权或有效额度 | 保存阻塞，继续独立部分 | 前提有效并完成原所需检查；获得前提不等于已经通过 |

网上资料可以说明常见做法、平台事实和研究方法，不替用户决定产品取舍，也不能证明本项目目标人群确有需求。研究或试验失败时保留反例，不能只摘取有利结果。

### 5）形成有依据的修订

写清原文、发现、建议、资料或观察、为何适用、代价和受影响对象。分别保存用户要求、建议和未知，不用建议覆盖正式原文。

研究或原型卡至少写：问题／假设 ID、关联产品决定、方法和招募／样本范围、实际环境和版本、授权与数据处理、前置条件和任务、事先定义的观察与判断方法、实际记录、结果、局限、下一动作。不能编造参与者、访谈、满意度、耗时或成功率。

低风险文案疑问可通过适用的文档走读处理，不强制所有项目做用户招募。关键用户行为假设若被明确列为进入条件，尚无所需真实依据时仍保留阻塞。

### 6）按影响复检与重新确认

保留修改前后，追踪受影响的需求、旅程、页面、功能、数据、验收、技术接口和任务。规则变化、边界变化、反例或来源失效触发重新判断。

需求、技术方案或权限实质变化须展示差异并取得相应阶段确认。用户已要求每阶段确认，产品自检不新增替代审批。只改表达也需核对是否改变原意；无需自动重做全部无关研究或试验，但复用依据必须说明影响评估。

旧证据保持原版本和环境；新版本受影响而尚未核查的对象标待复检。未重检的结果不改成当前版本满足。

### 7）出具结论并结束本轮

报告当前版本、范围、PC 分层检查、依据、问题、阻塞、主张证据、真实研究／试验和平台缺口、确认、预算及下一动作。量化分数支持定位薄弱环节，不代替关键阻塞、价值证据和用户确认。

可能的结论为：草案待补充、相关产品设计可交接、受影响任务阻塞、等待用户决定、因环境／预算暂停。任何结论只适用于声明范围。


## 4. 产品专属检查规则 PC01–PC15

“主要层次”是建议，检查开始时结合对象固定实际所需层次。每项满足都附对象版本、定位和依据；PC 数量不是功能数量，不能把“15 项都写了”当作完整覆盖。

| ID | 检查与适用性 | 具体满足条件 | 主要层次与记录 | 依据 |
| --- | --- | --- | --- | --- |
| PC01 | 用户、问题与价值依据；所有项目 | 明确实际或拟定使用者、场景、任务、困难和预期收益；事实、用户表达、建议、假设及未知分开；价值主张不超出证据；需验证的关键假设有结果或明确阻塞 | L1/L2；关键主张按需 L3。用户／问题／证据表 | Q07/Q21；PS01/PS02/PS04 |
| PC02 | 产品目标和成功判断；所有项目 | 目标描述用户结果，和问题一致；目标来源明确；“好用、快、稳定”等有适用判断方式或待决定；数值有来源、单位、环境和口径，不编造商业指标 | L1/L2；效果判断按需 L3。目标及成功口径 | Q09/Q17；PS01/PS04/PS06 |
| PC03 | 范围与优先级；所有项目 | 首版范围内外、必需与后续项清楚；优先级和理由有来源；不把建议当需求；必需任务链无遗漏；范围调整有影响和确认 | L1/L2。范围／优先级／差异记录 | Q07/Q13/Q22；PS01/PS02 |
| PC04 | 来源、假设与未知；所有项目 | 正式原文、用户决定、建议、参考资料、假设和未知分别标记且可定位；引用内容不替代授权；关键未知有影响、责任和下一动作；查证不超出资料适用范围 | L1/L2；重要假设按需 L3。来源与未知登记 | Q05/Q06；PS01/PS03/PS04 |
| PC05 | 完整用户旅程；关键用户任务必查 | 每个必需任务有入口、前置、连续动作、反馈、结果和适用退出；路径可达、没有依赖缺失；异常路线按实际风险；跨页面／会话任务衔接明确 | L1/L2；关键行为假设按需 L3。旅程与分支表 | Q08/Q21；PS04/PS05 |
| PC06 | 页面、导航与交互状态；有界面时；无界面说明入口 | 页面／窗口／入口关系、关键操作和导航明确；适用的空内容、加载、成功、错误、不可用状态有反馈和下一动作；目标平台交互约束已考虑 | L1/L2；理解／可操作主张按需 L3。页面与状态表 | Q08/Q09；PS01 的设计关联、PS05 的观察方法；具体状态要求为本项目细化 |
| PC07 | 功能输入和输出；全部适用功能 | 主体、触发、前置、输入类型与约束、正常行为、可见输出和副作用明确；限制与默认值有来源；功能卡足以区分成功和失败 | L1/L2。功能卡与字段表 | Q08；PS03 的明确／可验证原则；功能卡字段为本项目细化 |
| PC08 | 业务规则与状态；全部适用规则和状态 | 条件、分支、前后状态和数据变化一致；重复、顺序、冲突处理按能力明确；同一术语和规则跨页面／功能／验收一致；未定规则留决定事项 | L1/L2。规则／状态与冲突表 | Q08/Q13；PS03 的一致／明确原则；具体状态规则按本项目范围 |
| PC09 | 异常与边界；正常任务必查，其他按实际风险 | 适用的空／无效输入、重复、取消、中断、失败、恢复及依赖不可用有产品行为；提示、数据保留、下一动作和退出明确；不强制不存在的重试／撤销能力 | L1/L2；关键恢复／体验假设按需 L3。异常与边界矩阵 | Q08/Q14；PS02 的风险识别；具体矩阵为本项目细化 |
| PC10 | 数据、权限、费用与外部服务；副作用必查，具体项按能力 | 用户知道保存／修改／删除／分享什么；配置、默认和生效时机明确；账号／凭据／外发／收费／重复请求按有效决定设计；重要副作用不隐瞒、不越权 | L1/L2；实际前提按需 L3。用户数据与副作用表 | Q08/Q14/Q23 及有效用户决定；不是外部资料自动授予的权限 |
| PC11 | 产品质量与可理解性；声明目标及必要约束 | 体验、可用性、可访问性等按产品范围定义观察对象与判断方法；标签／提示一致并说明可行下一步；需要实际用户证明的主张有适用观察，不能由作者或模型自评替代 | L2；必要时 L3。质量目标／走读／原型记录 | Q09/Q15/Q17；PS05/PS06；具体质量目标来自项目范围 |
| PC12 | 验收设计；全部正式条件×适用平台 | 需求原文、平台、环境、数据、前置、操作、可判定断言和证据计划齐全；能验证用户任务而非只证明按钮存在；自动／人工方法和观察能力一致；缺环境仍留设计及阻塞 | L1/L2。验收卡与平台覆盖 | Q16/Q18/Q21；PS03/PS05/PS06 |
| PC13 | 正反追踪；全部需求、功能、任务与验收 | 每条需求有相符功能／流程和验收；每个新增产品行为有需求或已确认交付目的；追踪链接含义正确；未映射、遗漏、无来源副作用有处理 | L1/L2。双向追踪和孤立对象 | Q03/Q13；PS03 |
| PC14 | 产品与技术交接；进入规划及已有技术设计时 | 数据、权限、失败和体验承诺由明确技术对象承担；产品规则与接口、状态、数据、任务和测试一致；技术限制不静默改需求；不可行或未知先展示影响并分流 | L1/L2；核心可行性按需 L3。交接与差异表 | Q10/Q13/Q23；技术 TC02/TC04/TC05/TC07 |
| PC15 | 问题、版本、复检和确认；全部发现和阶段记录 | 检查对象／规则版本可定位；问题有依据、影响、状态和下一动作；关闭有对应修订／查证／复检和必要确认；旧记录保留；未关闭问题如实报告 | L1/L2。问题与版本台账 | Q06/Q20/Q22/Q23；技术 TC15 |

### 4.1 避免误判

- 有效用户表达可以支持“这是该用户提出的需求”，不能扩展成“所有同类用户都需要”。
- PC01/PC11 要求如实呈现证据程度；诚实说明假设并不自动证明产品价值。若该假设是必需交接条件，未验证时对应条件仍不满足或未核查。
- PC12 检查验收设计，不要求产品测试已经执行。真实测试是另一份结果记录；有测试设计不能记实际通过。
- PC15 检查台账合规，不要求所有问题已经解决。记录完整可以满足记录项，未解决的必需条件和对应阻塞仍存在。
- 不适用需要功能范围和理由；无资料、未完成、缺环境或难以检查都不能写不适用。
- 产品规则不能复制为未经确认的“行业最佳实践”；网上建议须说明采用理由与影响。


## 5. 问题卡、关闭、重开和阻塞

### 5.1 问题卡

每条问题记录：问题 ID、PC ID 与层次、对象版本、原文／位置、要求、实际发现、依据、影响需求／页面／功能／验收／技术／任务、严重程度及理由、是否阻塞及传播范围、处理类型、负责者、下一动作、结束条件、状态、修订差异、复检依据、必要确认、历史。

状态：**待处理 → 查证中／待用户决定／环境阻塞／修订中 → 待复检 → 已关闭**。失败、证据不足或决定未获得时回到相应未解决状态。暂停本轮不是问题关闭。

### 5.2 关闭按问题类型判断

| 类型 | 关闭要求 |
| --- | --- |
| 结构缺口 | 当前版本的规定字段／引用正确，并有核查记录 |
| 产品规则不清或冲突 | 当前设计明确、一致；受影响对象复核；实质取舍已有相应确认 |
| 用户或效果假设 | 取得事先要求的真实依据或由有效决定调整目标／范围；研究局限保留，不能凭改文字证明假设成立 |
| 技术可行性冲突 | 关联技术问题取得所需事实或实际试验依据；若改变产品／方案／权限取得相应确认 |
| 权限／费用／环境问题 | 前提已有效，随后完成原所需检查；获得权限或预算本身不算验收通过 |

问题结论为误报、重复或原条件不适用时，保留复核理由和关联记录。不得删除不利发现；关键反例重开关联问题，保留原关闭历史和新证据。

### 5.3 按影响阻塞

| 程度 | 例子与处理 |
| --- | --- |
| 关键 | 目标或基线冲突导致要做什么不明确；核心任务路径无法完成；越权数据外发／收费；可能重要数据损失；核心承诺不可行。阻塞受影响对象及依赖，需求／方案／权限变化回用户确认 |
| 重要 | 某功能、状态、规则或验收有具体缺口，不能据此可靠实施或判定。阻塞依赖该缺口的任务；独立工作可继续 |
| 一般 | 非关键表述或维护问题，已有明确行为和依据，当前任务可完成。记录修订与允许推进理由；若用户已定为必需条件仍阻塞 |

严重程度依据实际后果，不由关键词或分数决定。影响不明需先分析，不能直接降级。阻塞沿真实依赖传播，不因为同属一个文档就一律阻塞全部工作。


## 6. 版本、确认、预算和恢复

### 6.1 确认沿用已有四阶段

| 阶段 | 产品对象与核查重点 | 确认边界 |
| --- | --- | --- |
| 初始化 | 用户、问题、目标、范围、平台和约束，重点 PC01–PC04 | 用户确认当前初始化版本；未明事项保留 |
| 需求发现 | 场景、任务、候选需求、来源、假设和问题 | 用户确认当前发现结果；候选项不是自动正式需求 |
| 需求建模 | 旅程、功能卡、规则、状态、验收与追踪，重点 PC05–PC13 | 用户确认当前需求模型；关键未决规则明确阻塞 |
| 规划 | 质量、产品—技术交接、任务与验证设计，重点 PC12–PC15 | 用户确认当前规划；相关执行前条件另核查 |

这是按已有确认流程安排自检，不替用户确认，也不因文档达到某分数跳阶段。

### 6.2 版本影响

改需求／范围／规则，重检关联旅程、功能、页面、验收、技术和任务；改文案，核对原意和适用理解依据；改平台、外部服务或权限，重判交互、数据、成本和相关环境依据；发现新用户反例或资料冲突，重开关联问题。

确认绑定原版本；受影响变化需要新的对应确认。证据可在有记录的影响评估后复用，仍标原运行／研究版本与限制，不改成新一轮实际执行。

### 6.3 停止与恢复

本轮可在完成适用核查并出具报告、等待用户决定、用户暂停／取消、必要前提失效、有效时间／费用／调用／输出／资源额度到达、下一动作不能保证在剩余额度内时停止。重复处理没有新依据时依有效停止规则保留成果，不无限查网、招募、调用或试验。

预算和研究／试验授权来自有效用户决定；本文不设付费额度、不续期旧授权，也不允许自行联系他人。失败调用、重试和资源使用按有效口径计入，未知口径不能假设免费。

恢复时核对基线变化、决定、授权、环境和剩余额度；复检失效对象，继续未解决问题。本轮没有开展付费调用或真实研究活动。


## 7. 输出报告与量化边界

配套：[产品 SOP 量化指标](<PM量表.md>)及产品自检评分记录模板〔原资料：产品SOP自检研究/产品自检评分记录模板.md；未作为本模块运行依赖〕。

报告应逐项列出 PC ID、对象集合、适用性、所需层次、实际完成层次、满足／不满足／未核查／不适用、可定位依据、问题、阻塞范围和下一动作。统计按事先固定的对象及子项计算，不用 15 个大类标题数量替代真实覆盖分母。

文档质量评分、用户／价值主张证据、关键阻塞、阶段确认、真实产品通过分别呈现。结构字段完整不能给语义或真实研究层自动加分；缺环境或未核查的必需对象不移出分母；关键阻塞不能被其他维度高分抵消。

95 分如作为产品文档目标，是待确认的项目门槛建议；不因以前提出技术或整体评分就推定当前产品评分已批准。本文不产生真实项目分数，不证明用户需求或商业结果。
