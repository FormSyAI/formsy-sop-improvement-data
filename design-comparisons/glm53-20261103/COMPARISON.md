# 同一句需求，只差一份 SOP：计划阶段对照（GLM-5.3 真实跑）

> 一句话：**同一句功能请求、同一个模型、同一个温度，唯一差别是系统提示里有没有那 7 份 SOP 文件。**
> 结果，计划里 9 个「必须说清楚」的判定格，对照组做到 1 格，SOP 组做到 8 格。
> 而且差的不是篇幅——SOP 组的计划反而更短。

---

## 1. 实验设置

| 项 | 内容 |
| --- | --- |
| 模型 | `glm-5.3`（同一模型跑两组） |
| 接口 | `https://api.aurinova.cn/v1/chat/completions` |
| 参数 | temperature 0.2 / top_p 0.95 / max_tokens 7000 / reasoning_effort low |
| 种子 | 5201、5202、5203（三组独立重跑） |
| 阶段 | `initial`（只给需求原文）→ `final`（补发 7 条需求方答复后重跑） |
| 唯一变量 | 系统提示是否加载 FormSy SOP：7 个文件、39,172 字符 |
| SOP 版本 | 仓库 `formsy-sop`，`origin/main` @ `84908d7e` |
| 调用次数 | 3 seeds × 2 阶段 × 2 组 = **12 次真实调用**（全部留存 `response.json` + `answer.md`） |

两组共用的系统提示（一字不差）：

> 你是资深产品与项目 SOP 设计专家。根据用户需求撰写一份中文产品 SOP 和项目实施计划，覆盖范围、用户行为、状态、权限、数据与上下文、异常、制作任务和验收。必须区分已明确事实、建议和未知。不要把建议写成用户已确认的决定。不要进入代码实现…

**注意：这个提示词对对照组是"放水"的。** 它已经把"范围、状态、权限、上下文、异常、验收"这几项直接写进要求里了，等于把 SOP 的目录先给了它。真实开发场景里，没人会给这么全的清单。

## 2. 这个 case 是什么

用户在用自然语言查销售数据：上传一份销售表，然后连着问。

1. "去年各地区的销售额是多少？"
2. "华东地区增长最快的产品是什么？"
3. "把结果画成图。"

问完发现：**第二问问错了，应该是华南。**

产品要加两个按钮：改问题、删问题。开发请求只有一句话：

> 增加修改和删除历史问题的能力。修改问题后，结合之前的对话重新回答；删除问题时，同时删除这个问题及其后续回答，并更新对话历史。

听起来是两个按钮，真正要定义的是：**用户改掉了分析过程中的一步，整段分析应该怎么继续。**

用户会遇到三种坏体验：

- 改完之后，第 3 步的图还在，但画的是旧数据 —— 图和答案对不上。
- 改完重答失败，界面把旧答案又摆回来了 —— "华南的问题，配华东的答案"。
- 改的是**第一条**问题，一点提交就报错 —— 因为首条消息同时是会话的恢复锚点，换掉它，后端就接不上了。

第三条不是假设。这个项目上线后真实发生过：用户报"提交修改就报错"，诊断结论是**编辑第一条问题破坏了底层会话的恢复条件**。

---

## 3. 三处关键差异（逐字对照，不加解释）

判定口径：✓ 写清了（有处理方式、有后果）；△ 提到了但没定；✗ 没有。只计 ✓。

### A. 改完重答失败时，旧回答该不该回来？

| 组 | seed | 原文 | 判定 |
| --- | --- | --- | --- |
| 对照 | 5201 | "修改后重新生成失败…保留**原问题原回答**，显示错误提示+重试按钮" | ✗ 改动被静默吞掉 |
| 对照 | 5202 | "保留修改后的问题，回答区显示'生成失败，可重试'，不自动回滚问题文本" | ✓ |
| 对照 | 5203 | "保留**旧回答** + 显示错误提示 + 重试按钮；**问题文本已更新**" | ✗ 新问题配旧答案 |
| SOP | 5201 | "保留新问题文本…**旧回答不恢复（因基于旧问题）**；上下文中该问题标记为'未成功回答'" | ✓ |
| SOP | 5202 | "重新生成中（该位置显示加载态，**原回答已移除**）→ …失败（问题保留新文本，**无回答**）" | ✓ |
| SOP | 5203 | "历史保持修改后状态，该轮 `failed`…**不自动回滚问题文本**｜判定：重试成功后回答与修改后问题一致" | ✓ |

**计分：对照 1/3，SOP 3/3。**

这一条后来被需求方证实了。第 7 条补充答复：

> 修改后重新回答失败时，新问题文本保留，**旧回答和图表仍失效**；界面提供重试。

也就是说：在需求方开口之前，SOP 组 3 次全部押对，对照组 2 次押错。这不是文风差异，是**用户会看到什么**的差异。

### B. "改第一条问题"这个边界，有没有被当成一件事？

| 组 | seed | 原文 | 判定 |
| --- | --- | --- | --- |
| 对照 | 5201 | "修改/删除第一条问题｜允许；修改后**等于全新回答（无前置上下文）**" | △ 当成小事 |
| 对照 | 5202 | "【待定】：是否允许修改/删除第一个问题（删除后整个会话是否变为空会话…）" | △ 抛回需求方，未识别恢复风险 |
| 对照 | 5203 | 全文未出现"第一条问题" | ✗ 这个边界不存在 |
| SOP | 5201 | "SC-03｜删除首个问题｜删除 Q1｜对话清空，回到初始状态；**继续提问仅基于数据集**" | ✓ |
| SOP | 5202 | "X4｜删除第一条问题｜正常执行：整个对话只剩数据上传记录，**后续提问以空上下文开始**" | ✓ |
| SOP | 5203 | "修改首条问题｜同一般规则（首条之前无历史）｜正常重新回答" | △ |

**计分：对照 0/3，SOP 2/3。**

对照组三次里，没有一次把"改完第一条之后，这个会话还能不能继续用"写成一条可验收的东西。而线上事故就出在这里。

### C. 验收是"愿望清单"还是"判定表"？

| 组 | 形态 | 证据 |
| --- | --- | --- |
| 对照 5201 | 打勾清单 | 全文 0 处"断言"，`- [ ]` 若干条，如"修改后图表与新回答一致" |
| 对照 5202 | 打勾清单 | 13 个 `- [ ]`，0 处"断言"，0 个编号 |
| 对照 5203 | 有编号无判定方法 | AC1–AC10，但只写"应…"，没有操作步骤、没有判定方法、没有证据 |
| SOP 5201 | 断言表 | SC-01…SC-08，列头＝场景／操作／断言 |
| SOP 5202 | 断言表 | AC1…AC6，列头＝场景／前置／操作／**可判定断言** |
| SOP 5203 | 断言列＋证据计划 | 正常路径、异常路径各带"可验收断言"列；§7.3 写明"每条断言配操作录屏／截图 + 回答文本核对" |

**计分：对照 0/3，SOP 3/3。**

差别不在"写得全不全"，而在**写完能不能拿去判**。"修改后图表与新回答一致"不是断言，因为它没说什么叫一致、怎么看到一致。

### 合计

| | 对照 | SOP |
| --- | --- | --- |
| A 失败处置 | 1 / 3 | 3 / 3 |
| B 首条边界 | 0 / 3 | 2 / 3 |
| C 可判定验收 | 0 / 3 | 3 / 3 |
| **合计** | **1 / 9** | **8 / 9** |

## 4. 但篇幅是反过来的

| seed | 对照组字数 | SOP 组字数 |
| --- | --- | --- |
| 5201 | 4,893 | **4,511** |
| 5202 | 4,391 | 5,413 |
| 5203 | 4,669 | 5,069 |

seed 5201 里，SOP 组的计划**比对照组短 382 字**，但三处关键判定全部到位。所以差别不是"更长"，是"多出来的那几张表必须填"。

## 5. 补发 7 条答复之后：双方收敛

把需求方答复同时给两组，重跑：

| | 对照 | SOP |
| --- | --- | --- |
| 10 项必要点覆盖（seed 5201/5202/5203） | 9 / 9 / 9 | 10 / 10 / 9 |

对照组补齐了大部分。**唯一稳定没补齐的，仍是断言形式**：对照组依旧输出打勾清单，SOP 组依旧输出带判定列的表。

这条结论很重要，别讲成"用了 SOP 就一定更好"：

> SOP 不能替代需求方回答问题。它的作用是把"该问的问题"在你还没被问之前就摆到桌上。问题一旦被回答，两边的差距会迅速缩小——**剩下的差距，是"能不能验收"这件事，SOP 组没有丢。**

## 6. 是哪几条条款、在哪一步起了作用

对照实际加载的版本（`84908d7e`）：

| 计划里多出来的那一格 | 对应条款 | 逼出来的具体句子 |
| --- | --- | --- |
| 失败之后，这一轮停在什么状态 | `模块接口与数据.md` §6 场景填写表「错误、取消、超时与重复」＋ PC09 异常与边界（"提示、数据保留、下一动作和退出明确"） | "保留新问题文本…旧回答不恢复（因基于旧问题）" |
| 改第一条算不算一次正常迁移 | `模块接口与数据.md` §6 状态迁移填写表「无法迁移时的出口」＋ PC08 业务规则与状态 | "SC-03｜删除首个问题…继续提问仅基于数据集" |
| 这条验收怎么判 | PC12 验收设计（"前置、操作、可判定断言和证据计划齐全"） | SC-01…SC-08 表；AC1…AC6 表 |
| 历史存在内存里还是能重放 | `模块接口与数据.md` §7 数据对象填写表「保存与读取一致性」「生命周期」＋ PC14 产品与技术交接 | "对话历史持久化（是否已持久化：未知，若当前为内存态需新增持久化，属技术待承接）"；"H1：上下文由历史派生的实现机制（重放 vs 增量维护）" |

最后一行，就是线上事故的根因所在。SOP 没有预言这个 bug，但它逼着计划回答了"历史能不能重放"这个问题——对照组 3 份里，0 份问过。

## 7. 为什么会出现这个差别

不是模型变聪明了。是三件事变了：

1. **从"要写什么"变成"这张表必须填"。** 状态迁移表有列头：当前状态、事件、下一状态、数据/副作用、可见结果、**无法迁移时的出口**。最后一列不填，表就是空的，模型很难装作没看见。
2. **从"建议"变成"待承接"。** 对照组把"必须原子更新"写成结论（像是已经解决了）；SOP 组把它写成 H1/H2 待承接项，写明"重放还是增量维护、性能与费用影响未定"。**不知道就说不知道，这在计划阶段比写得漂亮更值钱。**
3. **从"验收标准"变成"可判定断言"。** 判定列一出现，"一致""正常""可用"这类词就过不了关，必须写成"改 Q2 后 Q3 文本仍在、A3 标记失效、上下文不含旧 A2"。

---

## 8. 改进了什么

- 计划评审时能拦住的问题变多了：以前是"看起来挺全"，现在是"这条断言怎么判？判不了就补"。
- "用户会看到什么"被提前写进计划，而不是等测试同学发现"华南的问题配华东的答案"。
- 边界（第一条、失败、并发）从"待定清单里的一行"变成"状态表里的一行 + 一条断言"，**待定的东西有归属，不会烂在文档里**。

一句话：**SOP 不负责让模型变聪明，它负责让"想没想到"这件事，变成"填没填"这件事。**

## 9. 复现与边界

```bash
cd ~/Desktop/test/FormSy-SOP-编辑删除历史问题对照-20261103
API_KEY=... python3 run_experiment.py --seed 5201            # initial
API_KEY=... python3 run_experiment.py --seed 5201 --clarification-file clarification.md   # final
```

- 产物：`runs/seed-<n>/<phase>/<arm>/{prompt.txt,response.json,answer.md}`；参数与 SOP 哈希见 `manifest-seed-<n>.json`。
- 边界：单模型（GLM-5.3）、单需求、3 个种子；9 个判定格为人工三档判定，不是自动打分。结论是方向性证据，不构成统计显著性。
- 对照组的提示词是"放水版"（已把验收、状态、异常写进要求）。按真实开发场景的提示词，差距只会更大，但本次没有跑那个变体。
