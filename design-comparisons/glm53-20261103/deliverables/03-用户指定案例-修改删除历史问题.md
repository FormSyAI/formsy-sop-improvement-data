# 用户指定案例：修改和删除历史问题

## 1. 表面需求

增加修改、删除历史问题的按钮。

真实需要设计的是：

- 修改第二个问题后，第一轮历史怎样保留？
- 原第二轮之后的结果是否失效、删除或重跑？
- 删除问题后，Agent 收到什么上下文？
- 修改或删除第一条问题还能不能正常工作？

## 2. 三个 seed 的初始设计

GLM5.3 的 Baseline 已能写出较完整设计，没有出现完全不懂场景的情况。

SOP 组更稳定地加入了：

- 事实、建议、未知分层。
- “界面历史是 Agent 上下文的唯一事实源”这一不变量。
- 修改后哪些回答和图表失效。
- 删除后历史与上下文同步移除。
- 删除首个问题后的空历史状态。
- 每条关键行为对应验收场景。
- 技术待承接项和剩余未知。

Baseline 的波动主要出现在：

- 有的 seed 把“第一条问题能否修改/删除”留成待确认。
- 有的 seed 没有在初始稿覆盖第一条问题的边界。
- 状态和验收虽然存在，但和同一条不变量之间的追踪不如 SOP 稳。

## 3. 共同澄清后的结果

两组收到完全相同的答复后，都明显改善，最终设计趋于接近。

共同答复包括：

- 任意问题包括第一条都可修改/删除。
- 修改后前序历史保留，当前及后续旧回答和图表失效。
- 后续问题文本保留，但系统不自动重跑。
- 删除后级联到对话末尾。
- 删除第一条后数据集保留。
- Agent 上下文只能使用界面中有效并展示的问答。
- 重答失败时保留新问题、旧回答失效并提供重试。

SOP 组的最终版仍然更强调：

- 单一事实源。
- 状态迁移的入口和出口。
- 失效内容不进入上下文。
- 失效问题重新执行时怎样组装上下文。
- 修改第一条问题、失效上下文和重答失败等独立验收。
- 哪些技术实现仍未承接。

## 4. 这个案例说明什么

这不是“Baseline 很差”的案例。强模型自己已经能提出大部分关键点。

它更适合说明：

> SOP 的价值是让本来能力较强的模型更稳定地想到边界，并把事实、状态、上下文、失败和验收串成一条可复核的链。

## 5. 对 SOP 的反向提醒

这个案例也说明，SOP 不能代替需求方决策。修改后后续问题到底删除、失效还是自动重跑，本来就应让需求方决定。SOP 应该帮助暴露选项和影响，不能把所有选项都写成已确认。
