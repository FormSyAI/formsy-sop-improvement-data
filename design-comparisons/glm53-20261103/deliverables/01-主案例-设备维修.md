# 主案例：实验室设备维修申请

## 1. 需求是什么

实验室设备发生故障后：

1. 使用人填写故障和设备影响程度并报修。
2. 维修人员接单、诊断，选择内部维修或转外修。
3. 维修完成后，使用人验收。
4. 设备维修期间不能继续预约。

这看起来是“做一个维修工单流程”，真正需要先定义的是：设备从哪一刻开始退出预约池，又从哪一刻重新进入预约池。

## 2. 不使用 SOP 的设计

Baseline 给出的流程总体完整：

`报修 → 待接单 → 接单 → 诊断 → 维修/外修 → 待验收 → 验收 → 完成`

它包含角色、权限、状态、异常、数据留痕和验收，也考虑了无人接单、外修超期、重复报修、验收驳回等场景。

但 Baseline 规定：

> 工单进入“已接单”及之后状态后，设备才被置为维修锁定。

这意味着：

- 使用人已经提交了故障报修；
- 维修人员还没有接单；
- 系统仍允许别人预约这台已经报修、状态未知的设备。

如果故障会影响安全或实验可靠性，这个时间窗口就是实际业务漏洞。

## 3. 使用 SOP 的设计

SOP 组规定：

> 使用人提交报修单后，系统生成“已提交”状态，并立即锁定该设备的预约。

设备状态从“正常”直接进入“维修锁定”，验收通过后才恢复可预约。

这不是简单的措辞差异，而是完整状态边界的变化：

| 问题 | Baseline | SOP |
|---|---|---|
| 何时开始不可预约 | 维修人员接单后 | 使用人提交报修后 |
| 报修到接单之间 | 仍可能被预约 | 已经退出预约池 |
| 何时恢复预约 | 验收通过后 | 验收通过后 |
| 预约系统不存在时 | 列为待确认 | 明确为技术阻塞，影响三条验收 |

## 4. SOP 为什么能补上这个点

主要不是 SOP 比模型“懂更多维修业务”，而是它要求模型按固定链路检查：

1. 用户任务从哪开始，到哪里结束。
2. 每个状态的前置、后状态和副作用是什么。
3. 关键状态有没有无人负责的空白区。
4. 核心副作用从哪一刻生效、何时解除。
5. 技术依赖不成立时，哪些验收不能算成立。
6. 每个功能是否能对应到验收。

对应条款：

- `PC05 完整用户旅程`：要求入口、前置、动作、反馈、结果和退出连续。
- `PC08 业务规则与状态`：要求前后状态和数据变化一致。
- `PC10 数据、权限与副作用`：要求配置、默认和生效时机明确。
- `PC12 验收设计`：要求环境、前置、操作和可判定断言齐全。
- `PC13 正反追踪`：要求功能和验收互相对应。
- `PC14 产品与技术交接`：要求技术限制不能被静默省略。
- `TC07 技术未知`：要求关键未知有影响、下一动作和阻塞关系。

## 5. 结果

- Baseline：流程看起来很完整，但把设备锁定晚了至少一个状态。
- SOP：先定义设备何时退出和恢复预约池，再写出对应验收。
- 对用户的直接价值：避免“已经报修的设备还能继续被预约”。
- 还需要确认：报修是否等同于确认故障，或是否需要增加“故障初步确认”状态。

## 6. 公平结论

不能把 Baseline 说成不会做维修流程。它已经写出了大部分维修业务。

更准确的结论是：

> Baseline 更擅长快速给出完整业务轮廓；FormSy SOP 更容易在状态衔接处追问“这个副作用从哪一步开始”，从而发现看起来完整但实际存在空窗的规则。
