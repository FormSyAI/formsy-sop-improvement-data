# 辅案例：企业培训作业提交

## 1. 需求

讲师发布作业和截止时间，学员上传文件提交；截止前可重新提交；讲师通过或退回补充；学员收到反馈。

## 2. 明显差异：重复点击与网络重试

Baseline 写的是：

> 多端同时提交时，以服务器时间为准，后提交覆盖并提示。

这在“用户确实要重新提交新版本”时合理，但没有区分两种情况：

- 用户主动重新提交一个新版本。
- 网络超时后重复点击，实际是同一个意图被发送两次。

SOP 组明确写：

> 重复点击提交必须幂等，不产生重复记录。

同时要求：

- 上传失败不留下半提交记录。
- 上传中断时保留上一个有效提交。
- 截止瞬间以服务器时间判断。
- 每次真正的重新提交保留历史版本，最新版参与批改。

## 3. 为什么这个差异重要

如果没有幂等边界，重复点击可能造成：

- 生成两个无意义版本。
- 讲师不知道该批哪一版。
- 学员误以为文件被覆盖。
- 审计记录看起来像两次真实提交。
- 验收无法区分“主动重交”和“网络重复”。

## 4. 对应 SOP 条款

- `PC08`：重复、顺序和冲突处理必须明确。
- `PC09`：失败、中断和恢复必须有产品行为。
- `PC10`：请求副作用和用户可见结果必须一致。
- `PC12`：每条验收必须有可判定断言。
- `TC04`：跨边界调用要考虑重复、超时和错误责任。
- `TC06`：关键正常操作、取消、部分失败和重复必须有状态/时序记录。

## 5. 结论

这个案例非常适合向非专业听众解释 SOP 的价值：

> 用户看到的是一个“提交”按钮，SOP 会继续问：网络重试后，它还是一个提交，还是会变成两个版本？

## 6. 边界

Baseline 也考虑了截止后提交、上传失败、退回补充和文件留痕。差异集中在“重复意图”与“真实重交”的区分，不能说 Baseline 完全没有异常设计。
