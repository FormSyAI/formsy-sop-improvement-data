## 项目规范、采集与报告

FormSy SOP owns the complete local development workflow. Start or continue the
workflow module under the user's existing authorization; the Server contributes
only Birdview, project SOP, and knowledge with Verifier. Their absence does not
disable built-in clarification, templates, planning, consistency, self-check,
implementation, repair or completion checks.

Use `formsy project connect --worktree ABSOLUTE --json` to prepare local resources
and attempt verified Server matching. A unique authorized match may bind;
ambiguous matches need an actual choice. Keep each repository's identity and
authorization independent. Read project_context/sop_get only for optional project
SOP, preserving its actual binding revision and published pin. Missing content
or a failed read remains a gap, never zero-rule success or fabricated permission.

The workflow module's optional-project-context reference owns source status,
adoption and local Verifier acceptance semantics. Raw JSON stays in files and
collapsed details; display brief progress, unresolved questions and the workbench.

## Apply shared Birdview guidance

Server supplies three optional project supplements: Birdview, project SOP, and
knowledge with Verifier definitions. Follow
[the source and acceptance contract](modules/formsy-sop-workflow/references/optional-project-context.md).
The workflow module owns their reads and local impact preview. Missing login,
binding, publication or connectivity does not disable the built-in SOP workflow.
Keep actual source identity, fixed versions and coverage gaps; availability is
not adoption, execution or acceptance. Applicable adopted Verifier failures
still hold acceptance; authorized result synchronization is tracked separately.

When MCP is not connected, describe the missing integration. If the user asks
for CLI diagnostics, discover the installed command through `formsy --help` before using it. The preview launch path is `formsy mcp serve`.

Report separately what the server returned, what remains unavailable, and what
was actually tested. Normal clarifications can remain in the current conversation.

## Record engineering milestones

Before engineering work, resolve the current session through the installed capture
configuration as described in the progress contract. A project/SOP lookup does not
establish native capture. When capture is configured, select and read back the
actual task before implementation. Reading this Skill or starting a watch does
not record the task. If binding is unavailable, report the specific attribution
gap and continue the user's ordinary authorized work without borrowing another
session's state. This applies independently of the development workflow.

For engineering work with an explicitly selected native FormSy capture state, read
[the progress contract](references/progress-recording.md) before starting work,
redirecting to a distinct deliverable, returning to a paused target, or recording
a material decision, verification, blocker or handoff. Check the current task
against the actual work target, not the overarching delivery goal. Same-target
tests and commits remain within that task. For task entry, the lifecycle contract
owns selecting actual user Activities and recording explicit trigger references.
Local progress does not require a selected or ready SOP. Follow the context's
legacy or explicit lifecycle interface; `formsy record` stores milestones.
Use legacy Evidence only when explicitly selected. MCP remains read-only.
Report the observed task receipt or the attribution gap in a short sentence,
not stored JSON. Skill selection is not an every-turn capture guarantee,
task approval or proof of completion.

## Render a supplied report

When the user requests a report and supplies actual project/SOP context or
explicitly asks to render supplied structured data, read
[the report contract](references/report-rendering.md). Use the supplied
[schema](references/report-v1.schema.json) and fixed
[renderer](scripts/render-report.mjs), with the existing
[HTML template](assets/development-report-v1.html). Fill data; keep template,
CSS and renderer unchanged. Never invent SOP or identity fields to bypass an
unready project. Label fixtures as fixtures and never use them as production
fallbacks.

After generating HTML, use the current client's available preview capability
to open it in this session. A queued/open request is not proof of rendered
display; otherwise return an absolute file link and explain the limitation.

## 开发流程模式写入 spec.md

specify/clarify 仍以 Spec Kit 的 spec.md 为唯一需求产物，实际读取上表的字段规范、模板与 PC 规则，将用户旅程映射 User Stories，行为映射 FR，验收映射场景和 SC，实体映射 Key Entities。来源、范围、未决与 PC 发现只补必要章节或已有检查报告，不另建平行 PRD/阶段状态。已有 R/A/J/F 等 ID 保留并映射到 US/FR/SC，禁止静默换号。按照既有任务授权推进，普通文档模式里的逐阶段确认要求不新增到开发流程模式。

## 完成当前任务

1. **固定范围。** 保留正式需求/验收原文、已有稳定 ID、当前版本和用户决定；区分生成 `generate`、整理 `organize`、评审 `review`。身份缺失用显式临时 ID 并登记缺口。用户只要局部草案或评审时继续可完成部分。
2. **核对原意。** 将要求、用户表达、外部事实、假设、候选建议和未知分开。新项目正式开始前，若还没有相应决定，先询问是否需要规划建议。按共同约定集中展示本模块全部当前已知首轮问题，每题独立、选项说明影响，允许连续选择或自由文本；后期新边界或冲突再逐题补问。已有有效回答不重问；“90%以上理解信心”不是统计证明或阶段确认。
3. **按阶段增量建模。** 初始化补用户/问题/目标/范围；发现补来源明确的候选需求和任务；建模补完整旅程、页面适用状态、功能输入/输出、业务转换、失败后数据与下一动作、质量及验收；规划补正反追踪和技术待承接。完成条件见阶段与来源。每阶段展示版本、差异、未决和影响；确认点按共同约定及当前用户决定，草案不冒称已批准。
4. **把行为写到可判断。** 用户任务须能从入口连续走到可识别终点。功能卡写触发/前置、输入类型与约束来源、正常顺序、可见输出、数据/权限/费用副作用、状态与异常、完成判据、验收和技术缺口。区分展示成功与真实完成。只展开适用能力；不为套模板新增登录、收费、重试、撤销或跨项目功能。
5. **分流未知并交接。** 用户取舍向用户澄清；外部事实按授权读取适用一手资料；用户需要/体验/效果主张需要相应真实依据；技术可行性写待承接项和所需查证/试验。没有实施授权只给计划和缺口。缺技术对象时保持待承接，不编造 MOD/API/DATA/T/TEST 或宣称交接通过。
6. **实际做基础自查。** 按 PC01–PC15 固定本次对象及适用性，走读正常和相关失败路径，核对页面/功能/规则/验收含义与反向来源。记录已完成的 L1/L2/必要 L3、依据、问题和影响；未核查不写满足，缺资料/环境/决定不写不适用。只评审时给具体定位与修订建议，未请求整理时保留原正文。
7. **交付并列结论。** 给当前产品 Markdown、来源与决定、实际 PC 检查、技术待承接、问题/阻塞、一个下一问题或下一动作。评分仅按请求另报；产品文档、价值支持、阶段确认、真实研究与应用验收分别呈现。95 分文档门槛仍是待确认建议；人工≤10%等用户目标仅按有效项目范围记录，不能写已达成。

## 来源、输出和运行边界

- 手工资料可同次明确采用固定版本/范围/用途；未明确采用或系统找到的资料先候选。采用不证明事实、不替阶段确认。引用带版本、片段及真实定位/读取范围；模型只接收本次相关且允许的片段。通用资料共享、项目资料隔离，跨项目须明确选取。
- 产品模块是项目的一份权威汇总 Markdown 的受控内容；模板与 `formsy-sop-0.2` 的章节 0/1/2/5/6/7/8 对齐，技术正文由实际承接后汇入。不得为同一产品规则造出互不一致的正式正文。
- handoff 的 `module` 为 `product`，`skill_name` 为 `formsy-sop-product`；记录契约、项目和对象版本。只有实际检查写进 `checks`。未执行应用验收时 `runtime_results=[]`，无真实确认时不填 `verified`。不能写“已保存”来代替实际文件工具结果。
- 输出 JSON 后，有 Python 工具时实际运行 `python3 scripts/validate_handoff.py /实际路径/handoff-product.json`，修复结构错误后再交付，并保存真实输出。此脚本只核对结构和引用；没有工具时注明结构脚本未运行，不能声称已通过。来源检查绑定来源自己的 revision，不使用当前产品模块修订代替。
- 只处理本次产品文档；不替用户批准技术栈，不执行开发、安装、部署、付费调用、用户招募或真实产品测试。需要这些动作时保留现有文档并交接授权/环境/预算缺口。

# 产品SOP自检方案：本模块相关部分

## 1. 为什么需要独立的产品自检

产品自检回答：这份 SOP 是否准确表达用户要解决的问题，能否说明用户如何完成任务，功能、交互、数据和验收是否一致，还有哪些产品取舍必须先决定？

技术自检回答：技术方案如何实现这些要求，模块、接口、数据和环境是否可行。两者以需求、功能和验收 ID 交接；分别保留产品问题和技术问题，不用技术方案合理替代产品目标合理。

现有规范已经包含产品检查，见 Q07/Q08/Q09/Q13/Q16/Q21〔原资料：sop-output-standard/references/质量检查表.md；未作为本模块运行依赖〕。缺口在于这些检查尚未展开为产品专属的适用规则、具体满足条件、证据、问题台账和复检过程。本文细化已有方向，不宣称产品检查从未存在。

### 1.1 各类结论分别记录

| 结论 | 回答什么 | 所需依据与限制 |
| --- | --- | --- |
| 产品文档检查 | 规定对象是否完整、一致、可理解、可交接 | 当前文档、规则、来源和分层核查记录；不等于真实产品已通过 |
| 技术文档检查 | 对应实现设计、交接和所需可行性是否就绪 | 使用独立技术规则及其所需查证／试验；不以产品文档分代替 |
| 产品主张得到支持 | 用户问题、任务或效果主张有哪些依据 | 原始表达、适用研究或真实观察；清楚标明样本、环境、限制和未验证假设 |
| 阶段用户确认 | 用户是否接受当前版本的目标、需求或规划 | 对应阶段和版本的有效用户决定；自检、资料和分数不能代替 |
| 实际产品验收 | 对应构建在目标环境能否完成正式条件 | 实际操作、文件、日志、截图及断言；文档、原型和单纯构建不能代替 |

私人使用的小工具可以根据使用者的明确要求形成设计，不强制市场调查。面向外部用户时，对“很多人需要”“能提高效率”“愿意付费”等主张要标明证据程度；PRD 字段齐全、作者自评和用户批准都不证明商业价值。

### 1.2 三层检查

| 层次 | 方法 | 可支持什么 | 不可推出什么 |
| --- | --- | --- | --- |
| L1 结构核查 | 按可重复规则查字段、占位、ID、引用、覆盖对象和版本 | 实际执行的结构规则满足或不满足 | 用户需要、流程可用、产品效果、试验完成 |
| L2 产品内容复核 | 按原始需求走读目标、任务、页面、功能、状态和验收；反向查越界；按适用性查外部事实 | 具体的行为一致性、缺口、冲突及依据范围内的设计判断 | 真实用户理解、全部场景可用、商业成立、用户批准 |
| L3 主张查证与真实研究／原型证据 | 针对事先明确的问题，记录实际访谈、观察、文档走读、原型任务或目标环境试验 | 在所述方法、样本和环境下取得的结果；不能扩大结论范围 | 最终产品全部通过、所有用户满意、其他平台通过 |

每条检查声明所需层次；正式资料可支持其明确说明的事实，不替代实际用户或原型试验。只有试验计划时记录“未执行”。模型提出用户画像、模拟用户或扮演评审，是建议与审查活动，不是实际用户研究。

检查状态：**满足 / 不满足 / 未核查 / 不适用＋理由**。真实研究或试验的观察、结果、限制独立记录；实际产品测试另记 **通过 / 失败 / 未验证 / 不适用＋理由**。三层未必都适用于每个对象，但所需层次尚未完成时不能把整项判满足。


## 2. 输入与输出对象

| 对象 | 最少内容 |
| --- | --- |
| 产品基线 | 项目、文档和规则版本；当前阶段；用户决定；使用者、范围、平台；原始资料定位和内容标识 |
| 用户与任务 | 已知用户和场景、要完成的任务、当前困难、目标结果；事实／建议／假设／未知分类 |
| 产品设计 | 范围和优先级、用户旅程、适用页面／入口、功能卡、状态规则、数据和权限行为 |
| 验收设计 | 需求和验收 ID、条件、环境、数据、操作、可观察断言、证据计划及平台适用性 |
| 检查清单 | PC01–PC15、对象集合、适用性、所需层次、满足条件及依据 |
| 研究或原型卡 | 问题与假设、方法、样本／环境、授权、事先判断口径、真实观察、结果及限制 |
| 问题台账 | 问题、定位、影响、严重程度、阻塞、处理者、下一动作、复检与历史 |
| 交接记录 | 产品对象→技术对象→任务→验收映射、冲突、待决定、当前阶段确认及影响 |

产品设计沿用现有 [功能设计卡和典型用户完整任务](<../assets/产品SOP模板.md>)，保留已有稳定 ID 和正式原文。技术映射使用 技术自检方案〔原资料：技术SOP自检研究/自检机制方案.md；未作为本模块运行依赖〕，不要求先写完代码才能核查产品文档。


## 3. 七步处理闭环

### 1）固定版本、对象和适用性

读取当前产品基线、原始资料、用户决定、平台和范围。固定需求、用户任务、功能、页面、状态、验收的对象清单及规则版本。无正式确认也可以核查草案，不能把草案结论变成已确认。

依据实际产品裁剪。例如无登录功能不要求设计登录页；没有外部付费服务不要求计费流程。范围不明确、资料缺失或环境不可用是待处理条件，不能为提高分数写“不适用”。

### 2）检查结构和引用

逐项检查必需字段、未填占位、重复编号、无效引用、来源身份、对象版本、必需需求及平台组合漏行。现阶段这些是检查规则方案，尚不能称应用已经自动执行了它们。

一个字段写了文字不表示内容满足。例如“失败时提示”没有说明提示和保留行为，应继续进入内容复核。

### 3）走读产品内容与完整任务

从用户任务起点开始，按正常和适用分支检查：入口→用户动作→系统反馈→状态和数据变化→最终结果或退出。逐条比较功能卡、页面、规则与验收；反向检查新增功能、权限、费用和数据外发是否有来源。

可安排另一位审阅者或另一轮复核，并保留异议和定位。同一模型重复自评不构成独立客观证据；有分歧时用原文、适用事实、真实观察或用户决定解决，不投票制造正确性。

### 4）把未知分流

| 未知 | 例子 | 下一动作 | 关闭依据 |
| --- | --- | --- | --- |
| 可查事实 | 目标平台的交互约束、外部服务支持和错误含义 | 查一手资料，记录版本和适用性 | 可定位依据支持所需事实，冲突得到解释 |
| 用户取舍 | 删除是否可撤销、自动覆盖还是另存、数据外发与费用 | 展示选项、后果和建议；逐个询问影响最大的事项 | 当前版本的有效用户决定 |
| 用户问题或效果假设 | 特定任务是否困难、用户能否理解、流程是否节省时间 | 根据影响设计适用的访谈、观察或原型任务；只执行已授权活动 | 实际记录和事先口径，明确样本与结论限制 |
| 技术可行性 | 目标平台能否按产品承诺运行、恢复数据 | 关联技术问题与验证卡 | 技术查证或所需实际试验结果，不能仅因写好设计关闭 |
| 环境／权限／预算阻塞 | 无目标环境、缺必要授权或有效额度 | 保存阻塞，继续独立部分 | 前提有效并完成原所需检查；获得前提不等于已经通过 |

网上资料可以说明常见做法、平台事实和研究方法，不替用户决定产品取舍，也不能证明本项目目标人群确有需求。研究或试验失败时保留反例，不能只摘取有利结果。

### 5）形成有依据的修订

写清原文、发现、建议、资料或观察、为何适用、代价和受影响对象。分别保存用户要求、建议和未知，不用建议覆盖正式原文。

研究或原型卡至少写：问题／假设 ID、关联产品决定、方法和招募／样本范围、实际环境和版本、授权与数据处理、前置条件和任务、事先定义的观察与判断方法、实际记录、结果、局限、下一动作。不能编造参与者、访谈、满意度、耗时或成功率。

低风险文案疑问可通过适用的文档走读处理，不强制所有项目做用户招募。关键用户行为假设若被明确列为进入条件，尚无所需真实依据时仍保留阻塞。

### 6）按影响复检与重新确认

保留修改前后，追踪受影响的需求、旅程、页面、功能、数据、验收、技术接口和任务。规则变化、边界变化、反例或来源失效触发重新判断。

需求、技术方案或权限实质变化须展示差异并取得相应阶段确认。用户已要求每阶段确认，产品自检不新增替代审批。只改表达也需核对是否改变原意；无需自动重做全部无关研究或试验，但复用依据必须说明影响评估。

旧证据保持原版本和环境；新版本受影响而尚未核查的对象标待复检。未重检的结果不改成当前版本满足。

### 7）出具结论并结束本轮

报告当前版本、范围、PC 分层检查、依据、问题、阻塞、主张证据、真实研究／试验和平台缺口、确认、预算及下一动作。量化分数支持定位薄弱环节，不代替关键阻塞、价值证据和用户确认。

可能的结论为：草案待补充、相关产品设计可交接、受影响任务阻塞、等待用户决定、因环境／预算暂停。任何结论只适用于声明范围。


## 4. 产品专属检查规则 PC01–PC15

“主要层次”是建议，检查开始时结合对象固定实际所需层次。每项满足都附对象版本、定位和依据；PC 数量不是功能数量，不能把“15 项都写了”当作完整覆盖。

| ID | 检查与适用性 | 具体满足条件 | 主要层次与记录 | 依据 |
| --- | --- | --- | --- | --- |
| PC01 | 用户、问题与价值依据；所有项目 | 明确实际或拟定使用者、场景、任务、困难和预期收益；事实、用户表达、建议、假设及未知分开；价值主张不超出证据；需验证的关键假设有结果或明确阻塞 | L1/L2；关键主张按需 L3。用户／问题／证据表 | Q07/Q21；PS01/PS02/PS04 |
| PC02 | 产品目标和成功判断；所有项目 | 目标描述用户结果，和问题一致；目标来源明确；“好用、快、稳定”等有适用判断方式或待决定；数值有来源、单位、环境和口径，不编造商业指标 | L1/L2；效果判断按需 L3。目标及成功口径 | Q09/Q17；PS01/PS04/PS06 |
| PC03 | 范围与优先级；所有项目 | 首版范围内外、必需与后续项清楚；优先级和理由有来源；不把建议当需求；必需任务链无遗漏；范围调整有影响和确认 | L1/L2。范围／优先级／差异记录 | Q07/Q13/Q22；PS01/PS02 |
| PC04 | 来源、假设与未知；所有项目 | 正式原文、用户决定、建议、参考资料、假设和未知分别标记且可定位；引用内容不替代授权；关键未知有影响、责任和下一动作；查证不超出资料适用范围 | L1/L2；重要假设按需 L3。来源与未知登记 | Q05/Q06；PS01/PS03/PS04 |

| PC07 | 功能输入和输出；全部适用功能 | 主体、触发、前置、输入类型与约束、正常行为、可见输出和副作用明确；限制与默认值有来源；功能卡足以区分成功和失败 | L1/L2。功能卡与字段表 | Q08；PS03 的明确／可验证原则；功能卡字段为本项目细化 |

### 4.1 避免误判

- 有效用户表达可以支持“这是该用户提出的需求”，不能扩展成“所有同类用户都需要”。
- PC01/PC11 要求如实呈现证据程度；诚实说明假设并不自动证明产品价值。若该假设是必需交接条件，未验证时对应条件仍不满足或未核查。
- PC12 检查验收设计，不要求产品测试已经执行。真实测试是另一份结果记录；有测试设计不能记实际通过。
- PC15 检查台账合规，不要求所有问题已经解决。记录完整可以满足记录项，未解决的必需条件和对应阻塞仍存在。
- 不适用需要功能范围和理由；无资料、未完成、缺环境或难以检查都不能写不适用。
- 产品规则不能复制为未经确认的“行业最佳实践”；网上建议须说明采用理由与影响。


## 5. 问题卡、关闭、重开和阻塞

### 5.1 问题卡

每条问题记录：问题 ID、PC ID 与层次、对象版本、原文／位置、要求、实际发现、依据、影响需求／页面／功能／验收／技术／任务、严重程度及理由、是否阻塞及传播范围、处理类型、负责者、下一动作、结束条件、状态、修订差异、复检依据、必要确认、历史。

状态：**待处理 → 查证中／待用户决定／环境阻塞／修订中 → 待复检 → 已关闭**。失败、证据不足或决定未获得时回到相应未解决状态。暂停本轮不是问题关闭。

### 5.2 关闭按问题类型判断

| 类型 | 关闭要求 |
| --- | --- |
| 结构缺口 | 当前版本的规定字段／引用正确，并有核查记录 |
| 产品规则不清或冲突 | 当前设计明确、一致；受影响对象复核；实质取舍已有相应确认 |
| 用户或效果假设 | 取得事先要求的真实依据或由有效决定调整目标／范围；研究局限保留，不能凭改文字证明假设成立 |
| 技术可行性冲突 | 关联技术问题取得所需事实或实际试验依据；若改变产品／方案／权限取得相应确认 |
| 权限／费用／环境问题 | 前提已有效，随后完成原所需检查；获得权限或预算本身不算验收通过 |

问题结论为误报、重复或原条件不适用时，保留复核理由和关联记录。不得删除不利发现；关键反例重开关联问题，保留原关闭历史和新证据。

### 5.3 按影响阻塞

| 程度 | 例子与处理 |
| --- | --- |
| 关键 | 目标或基线冲突导致要做什么不明确；核心任务路径无法完成；越权数据外发／收费；可能重要数据损失；核心承诺不可行。阻塞受影响对象及依赖，需求／方案／权限变化回用户确认 |
| 重要 | 某功能、状态、规则或验收有具体缺口，不能据此可靠实施或判定。阻塞依赖该缺口的任务；独立工作可继续 |
| 一般 | 非关键表述或维护问题，已有明确行为和依据，当前任务可完成。记录修订与允许推进理由；若用户已定为必需条件仍阻塞 |

严重程度依据实际后果，不由关键词或分数决定。影响不明需先分析，不能直接降级。阻塞沿真实依赖传播，不因为同属一个文档就一律阻塞全部工作。


## 6. 版本、确认、预算和恢复

### 6.1 确认沿用已有四阶段

| 阶段 | 产品对象与核查重点 | 确认边界 |
| --- | --- | --- |
| 初始化 | 用户、问题、目标、范围、平台和约束，重点 PC01–PC04 | 用户确认当前初始化版本；未明事项保留 |
| 需求发现 | 场景、任务、候选需求、来源、假设和问题 | 用户确认当前发现结果；候选项不是自动正式需求 |
| 需求建模 | 旅程、功能卡、规则、状态、验收与追踪，重点 PC05–PC13 | 用户确认当前需求模型；关键未决规则明确阻塞 |
| 规划 | 质量、产品—技术交接、任务与验证设计，重点 PC12–PC15 | 用户确认当前规划；相关执行前条件另核查 |

这是按已有确认流程安排自检，不替用户确认，也不因文档达到某分数跳阶段。

### 6.2 版本影响

改需求／范围／规则，重检关联旅程、功能、页面、验收、技术和任务；改文案，核对原意和适用理解依据；改平台、外部服务或权限，重判交互、数据、成本和相关环境依据；发现新用户反例或资料冲突，重开关联问题。

确认绑定原版本；受影响变化需要新的对应确认。证据可在有记录的影响评估后复用，仍标原运行／研究版本与限制，不改成新一轮实际执行。

### 6.3 停止与恢复

本轮可在完成适用核查并出具报告、等待用户决定、用户暂停／取消、必要前提失效、有效时间／费用／调用／输出／资源额度到达、下一动作不能保证在剩余额度内时停止。重复处理没有新依据时依有效停止规则保留成果，不无限查网、招募、调用或试验。

预算和研究／试验授权来自有效用户决定；本文不设付费额度、不续期旧授权，也不允许自行联系他人。失败调用、重试和资源使用按有效口径计入，未知口径不能假设免费。

恢复时核对基线变化、决定、授权、环境和剩余额度；复检失效对象，继续未解决问题。本轮没有开展付费调用或真实研究活动。


## 7. 输出报告与量化边界

配套：[产品 SOP 量化指标](<PM量表.md>)及产品自检评分记录模板〔原资料：产品SOP自检研究/产品自检评分记录模板.md；未作为本模块运行依赖〕。

报告应逐项列出 PC ID、对象集合、适用性、所需层次、实际完成层次、满足／不满足／未核查／不适用、可定位依据、问题、阻塞范围和下一动作。统计按事先固定的对象及子项计算，不用 15 个大类标题数量替代真实覆盖分母。

文档质量评分、用户／价值主张证据、关键阻塞、阶段确认、真实产品通过分别呈现。结构字段完整不能给语义或真实研究层自动加分；缺环境或未核查的必需对象不移出分母；关键阻塞不能被其他维度高分抵消。

95 分如作为产品文档目标，是待确认的项目门槛建议；不因以前提出技术或整体评分就推定当前产品评分已批准。本文不产生真实项目分数，不证明用户需求或商业结果。

## 生成或整理

1. 将需求/行为/验收映射到设计，反查每个新增模块、依赖、权限和任务的来源。技术支持动作可以关联交付目的，不据此增加用户功能。
2. 按稳定责任、数据所有者和信任边界划模块；小项目允许同进程或合并实现，契约责任仍清楚。必要动作有主负责方，失败传播与依赖方向可说明。
3. 模块卡写清输入校验、成功语义、接口与状态、唯一写入方、错误责任及取消/重复/恢复。对关键接口核对提供方与调用方；“已接收”不能充当“已持久保存”。
4. 数据模型说明约束、提交边界、失败保留、生命周期和适用的迁移/删除/恢复。用关键真实用户路径走读正常与反例，状态图、数据写入及反馈互相一致。
5. 将未知分为事实查证、核心假设试验、用户取舍和环境/权限/预算阻塞。技术事实按授权使用对应版本的一手来源；必须在目标环境证明的假设有事先判定条件，实际未做就保留未验证。
6. 全局计划保留完整目标和依赖；临近任务细化为输入、进入条件、步骤、产出、断言、停止和恢复。前任务只承诺当前可验证的子断言，依赖后任务的完整行为留到集成任务并列真实前置。状态/名单重置不能解除历史批准形成的变更门槛。每项验收按适用平台设计操作与证据；缺环境不删除平台、不继承另一平台通过。
7. 完整设计先固定资产、数据流和信任边界，再按实际能力展开安全专项。将威胁 TH、控制 CTRL、MOD/API/DATA、测试与证据版本绑定；SEC01–SEC12 在交接使用 `CUSTOM:SEC01` 等，不改 TC 原编号。加密、凭据保存、桌面配置和更新策略按实际平台及有效决定设计；候选选型不称已实施，安全用例未运行不称控制有效。部分修订只复核实际影响范围，并说明未审阅部分。
8. 将临近实施的任务拆到执行者可按卡开始：固定输入/对象版本、允许改动、依赖/进入条件、每步操作与中间结果、产物、可观察完成断言和验证、停止/取消恢复；文件和命令未定位不编造。实现与对应验证同任务闭环，另保留集成和完整用户路径任务。重要未知拆成查证/待决定，不把受阻实施写成ready；用TASK01–TASK10复核，粒度不足继续拆，已满足时停止无意义分割。

使用 [技术模板](assets/technical-template.md)组织输出。可以裁剪确实不适用的章节并记录理由；不能用占位表、库名称或“待后续”掩盖关键缺口。性能阈值、额度和重试次数有来源或待决定，不填任意数字。

## 评审和基础自查

用 TC01–TC15 覆盖本次技术对象，记录适用性、对象版本、定位、L1 结构/L2 语义/L3 所需查证与证据。缺资料是未核查或不满足，不是不适用；未做所需试验不能把其余层的满足汇总成整项满足。

使用 [技术评审模板](assets/technical-review-template.md)逐条输出实际发现、影响任务和下一动作。文档冲突按当前内容复检；实际可行性失败按规定环境重测。修改建议、问题台账完备与问题已关闭分别报告，高分不解除阻塞。涉及需求、方案或权限实质改变时展示差异并回相应阶段确认。

# 自检机制方案：本模块相关部分

## 1. 自检要回答什么

对普通使用者而言，自检最终需要回答：这份流程是否说清了要做什么、由什么模块完成、数据如何处理、遇到问题怎么办、如何确认完成，还有什么必须先解决？

自检输出应是有依据的问题与结论。不能仅输出“内容完整”“建议完善错误处理”或一个模型自评分。

技术摘要适合快速介绍；模块、运行场景、决定、质量与风险仍需展开。这个划分借鉴 [arc42 方案概述](https://docs.arc42.org/section-4/)及其[运行场景](https://docs.arc42.org/section-6/)。

### 1.1 三层检查与证据边界

| 层次 | 检查对象及方法 | 可支持的结论 | 不能由此推出 |
| --- | --- | --- | --- |
| L1 结构检查 | 字段、ID、引用、版本、依赖、关联格；采用可重复程序规则，核查误报 | 规定的结构规则满足或不满足 | 设计合理、核心方案可行、功能实际通过 |
| L2 语义复核 | 需求含义、模块职责、接口双方、数据/状态、任务/验收一致性；逐条追踪、资料查证及独立复核 | 在声明范围内有依据的设计判断或具体冲突 | 模型无误、试验完成、用户批准 |
| L3 可行性查证 | 核心假设所需的平台、版本及实际环境依据；官方资料和必要的原型/操作/文件/日志核查 | 对明确假设取得相应依据；实际试验单列通过/失败/未验证 | 最终产品、其他平台或所有未来情况已通过 |

每条规则指定需要哪些层次。官方资料可支持它明确说明的版本事实，不能证明本项目实现已成功运行。规则要求实际试验而未执行时，不能因已有试验计划计满足。

检查状态为 **满足 / 不满足 / 未核查 / 不适用＋理由**；实际试验状态为 **通过 / 失败 / 未验证 / 不适用＋理由**。两者分列，不将“设计满足”显示成“产品通过”。

### 1.2 来源事实与本项目规则

arc42 提供文档划分和代表性场景方法；NASA 提供设计审查、需求追踪和原型验证指导；MADR 提供技术决定记录结构；Google SRE 提供有实际动作、可裁剪的准备检查方法。来源支持方法，**不共同规定本文件的检查编号、严重程度、状态流和停止条件**，这些是本项目建议。用户批准与项目预算也不能从资料推导。

Google SRE 方法见[发布准备原文](https://sre.google/sre-book/reliable-product-launches/)；各来源的版本及本项目采用范围见参考资料索引。

不要求所有应用具备取消、重试、升级或全部异常场景。适用范围由已确认目标、实际能力和风险决定；不适用要留理由，关键风险不能为提高分数删除。


## 4. 技术检查清单

状态统一为：**满足 / 不满足 / 未核查 / 不适用＋理由**。每项必须附定位和依据；占位值、“以后再说”和未经核查的模型断言不计满足。

| 检查 ID | 检查对象与问题 | 应得到的记录 | 主要依据 |
| --- | --- | --- | --- |

### 4.1 适用性与具体满足条件

下表补充上表。每个项目开始检查时固定对象清单和适用项；子项不适用记录理由，不能因缺数据或缺环境移出分母。纯本地小应用可合并模块/数据记录，无需套用云系统组织结构。

| ID | 适用性 | 具体满足条件 |
| --- | --- | --- |
| TC01 | 所有项目 | 对象/规则版本和范围可定位；有效决定、目标平台明确；草案/已确认分开，基线冲突不隐藏 |
| TC02 | 所有项目 | 每条适用需求有内容正确的设计、任务、验收关联；设计反向有需求或交付目的；缺口/孤立对象有处理记录 |
| TC03 | 所有项目；层次按规模 | 职责、边界、输入输出、数据归属、依赖、失败责任清楚；必要动作无无人负责或冲突负责；依赖满足声明约束 |
| TC04 | 跨模块/进程/文件/服务边界；无独立边界要说明 | 双方输入类型/约束、输出、错误、权限和版本一致；适用调用顺序、超时/重复/兼容行为明确；关键未知转 TC07 |
| TC05 | 数据必查；持久化/敏感数据/迁移按范围 | 类型、约束、归属、生命周期、读写明确；需保存时有失败保留/恢复；需删除/迁移时有范围/后果；关键假设取得所需依据 |
| TC06 | 正常关键操作必查；其他场景按能力及风险 | 适用场景有前状态、事件、状态/数据变化、可见结果和失败责任；关键可达状态无未说明出口；不支持的行为有明确边界 |
| TC07 | 所有项目先识别未知；关键假设需查证 | 未知分类、影响与下一动作明确；影响核心实施的假设取得事先要求的资料或实际试验依据；失败/未验证不算解决 |
| TC08 | 已声明及范围必要的质量约束 | 触发、环境/规模、响应、判断方法明确；数字有单位/来源；无依据登记待决定/待测，不自行编造阈值 |
| TC09 | 权限/副作用必查；凭据/外发按实际能力 | 信任边界、必要权限、数据流和保护/生命周期明确；副作用在有效决定内；新增或未知权限不默许 |
| TC10 | 使用外部库/工具/服务/复用代码时 | 版本、许可义务、目标环境、关键限制可查证；关键依赖失效有影响和可行处理；低风险依赖不强制备份技术栈 |
| TC11 | 交付环境必查；安装/升级/回退按范围 | 各平台运行/交付前提明确；适用兼容、失败和恢复行为具体；环境缺口保留；首版未承诺升级需说明边界 |
| TC12 | 全部适用验收×平台组合 | 前置、环境、数据、操作、可判定断言、证据计划齐全；自动/人工方法与观察能力一致；缺环境仍有设计，真实运行另列 |
| TC13 | 全部验收设计与关键试验 | 断言验证原需求行为/结果；关键反例按风险覆盖；不以文件、按钮或实现存在代替功能完成 |
| TC14 | 外部依据与继承证据；本地决定亦绑定版本 | 来源/版本/日期/位置及适用性明确；主张不超出资料；冲突/失效保留；依据复用有影响评估 |
| TC15 | 所有发现；无发现亦需复核记录 | 问题有影响、状态、下一动作；关闭有依据和复检；变更/反例触发重开或失效评估；暂停/取消不算关闭 |

每条检查按 L1/L2/L3 分别留结果；所需层次未完成时，不把其他层的满足当成整项满足。凭据检查的报告应脱敏，不能为了定位问题复制真实秘密。

层次建议：TC01/TC02/TC03/TC12/TC14/TC15 以 L1 和 L2 为主；TC08/TC09/TC10/TC11 以 L2 为主，结构字段可另做 L1；TC04/TC05/TC06/TC07 除设计复核外，按关键假设决定是否需要 L3；TC13 以 L2 为主。具体对象已有有效资料可回答事实时不强制试验；必须依赖目标环境证明的假设不能省去 L3。


## 5. 问题台账与关闭标准

每条问题记录：问题 ID、检查 ID 与层次、对象版本与位置、预期规则、实际发现、依据、影响对象/任务、严重程度与理由、是否阻塞及理由、处理类型、需要谁处理、下一动作、结束条件、状态、修改前后、复检结果与证据、历史。

问题状态：**待处理 → 查证中 / 待用户决定 / 环境阻塞 / 修订中 → 待复检 → 已关闭**。分流可以调整；失败或依据不足返回待处理或相应阻塞状态，保留尝试历史。

**已关闭的最低条件：** 原问题有具体修订或查证结果；依据支持对应结论；关联检查满足；受影响对象已复核；需要确认的变化已有有效确认。删除问题行或把状态改成“已处理”不满足关闭条件。

每个来源的完整摘要不必重复抄入问题卡，引用来源 ID 和准确位置即可。

关闭依据按问题类型选择：无效引用修复用当前文件的引用核查；设计冲突修订用契约/语义复检；实际可行性失败用规定的目标环境重测。文档问题不一律要求运行应用，实际试验问题也不能仅凭改文档关闭。

TC15 检查台账和处理/复检记录是否真实、完整、符合当前状态，**不是要求所有问题均已关闭**。诚实保留未关闭问题、下一动作和阻塞可以满足对应审计记录项；事先要求完成但尚未执行的修订/复检项仍不满足或未核查，相关任务仍未就绪。记录合规、处理完成、项目就绪分别汇报。

### 5.1 严重程度与相关任务阻塞

| 等级 | 判定依据 | 处理建议 |
| --- | --- | --- |
| 关键 | 违反有效需求/权限决定；核心方案不可实施或依赖未查证关键假设；可能造成重要数据损失/越权；基线冲突使执行对象不明 | 阻塞受影响任务及其实际依赖；需求/方案/权限变化提交用户决定；跨阶段基线问题可能影响整个阶段 |
| 重要 | 接口、数据、状态、验收等有具体缺口，使相关实现不能据此可靠完成或评判，但影响可定位 | 阻塞依赖该缺口的任务；独立部分可继续，留下依赖边界和理由 |
| 一般 | 表述、维护或非关键细节问题；已有明确设计及依据，当前任务仍能按要求完成 | 留修订安排和允许推进的理由；若属于用户确认的必需门槛仍阻塞 |

等级依据实际影响，不按关键词或单个模型分数自动决定；未授权的新权限/副作用不能降级后继续。事实不足可标“严重程度待判断”，关键风险相关部分仍未就绪。

阻塞范围从问题定位到需求、模块、接口、数据、平台和任务，再沿实际依赖传播并说明理由；不要仅因同属一份文档阻塞无关任务。影响范围不明时登记分析缺口；不依赖该问题的资料整理、设计复核或其他已授权工作可继续。解除阻塞须记录当前版本复检与有效确认的依据。

### 5.2 状态变化、重开与误报

| 变化 | 必要记录与边界 |
| --- | --- |
| 待处理→查证/修订 | 下一动作、责任、授权/预算和结束条件；开始处理不等于解决 |
| 处理状态→待复检 | 实际修订或查证结果、差异、影响范围和证据；生成建议不等于关闭 |
| 待复检→已关闭 | 原问题得到回答、依据适用、原规则满足、相关对象重检、必要确认有效 |
| 已关闭→重开 | 新事实/反例、版本变化或关闭判断错误；新一轮关联旧记录并回到待处理/相应分流，不覆盖原关闭历史 |
| 本轮暂停/取消 | 保存原因、未解决项、成果、额度使用和恢复条件；这是轮次状态，不是问题关闭 |
| 复核为误报/重复 | 保留规则、事实、范围理由或关联原问题及复核记录；不能用“非问题”掩盖尚未回答的缺口 |

可拆分关联问题：“缺少可行性试验计划”与“关键技术假设未验证”。前者补全设计后可复检关闭；后者必须取得所需依据，不能因计划完善一起关闭。

### 5.3 版本影响与证据有效性

检查、问题、来源、试验和决定绑定对象版本、平台与环境。同名文件改动后，不能继续默认沿用原检查结果。

| 变化 | 影响评估与复检 |
| --- | --- |
| 文案/定位调整 | 核对是否仅改变表达，不改变行为、条件、边界或承诺；保留差异与理由，不自动要求全部试验重跑 |
| 接口/数据/状态/依赖变更 | 追踪调用方、消费者、场景、任务及验收；受影响结论待复检，实际试验按影响重做 |
| 需求/方案/权限实质变化 | 新内容待确认；保留原版本和决定；取得相应阶段确认后推进相关执行 |
| 平台/环境/依赖/规则版本变化 | 重新判断适用范围与支持的结论；新平台不继承另一平台的实际通过；规则变更重算相关口径 |
| 新资料推翻旧依据或发现遗漏 | 保留冲突、影响与重开理由，按最新有效基线复检 |

设计结论、用户确认和实际证据分别判断有效性。旧依据可在有记录的影响评估后复用，旧实际执行记录仍保留原版本/环境；不改写成新一轮通过。部分不受影响不代表整个新基线已就绪。

### 5.4 预算、停止与恢复

本轮停止条件包括：适用检查已完成并报告；需要用户决定；有效调用/输出/时间/费用/资源限制到达；下一动作无法保证在剩余额度内；同一关键问题按有效停止规则重复处理却无新依据；用户暂停/取消；关键前提失效。

具体次数、重试与费用限制来自有效授权，本方案不自定付费上限。失败请求、重试和其他调用如何计次/计费按授权口径与服务记录核对；口径不明不假定免费或不计次。达到限制保存候选成果、问题、尝试历史和停止原因，不无限重试。本轮没有调用用户配置的模型 API。

恢复时读取停止记录和最新基线，检查决定、权限、环境、预算是否仍有效；核对剩余额度；分析变更影响并重检失效项。过期预算不自动续期，取消后的成果也不自动代表恢复已获授权。没有目标环境的关键试验仍未验证。

报告列出基线/规则版本、适用与不适用范围、分层结果、量化分母、问题和影响任务、真实试验/平台缺口、待决定、预算及下一动作。建议相关任务就绪条件为其阻塞项解决、适用必需检查满足、核心假设取得所需依据及当前阶段确认有效；正式门槛须用户确认。报告记录满足不代表所有修订或试验均已完成。

自检支持用户审阅，不能替用户点击确认、接受需求变化或完成最终验收。高分不解除阻塞，详见 量化评判指标〔原资料：技术SOP自检研究/量化评判指标.md；未作为本模块运行依赖〕。

### 3.2 模块划分原则

1. 按稳定责任、数据所有权、信任边界和变化原因划分；一个模块有可描述的主责任，必要动作有唯一的主负责方。
2. 业务规则与显示交互、持久化、外部服务和知识资料治理分出明确边界；它们可以在同一进程内实现，不要求多服务部署。
3. 拆分应降低耦合并使失败、验证和恢复可处理。过度通用、重复封装和没有当前用途的模块需说明理由；小项目可合并实现，但契约责任仍清楚。
4. 数据写入、状态推进和错误处置明确由谁拥有；调用方不能绕过所有者直接修改数据或猜测成功。
5. 依赖方向避免循环；确需回调或事件时说明事件所有者、顺序、重复与失败处理，不能用“异步”隐藏一致性问题。
6. 共享支持模块通过接口供产品设计、技术设计和自检使用。知识库独立治理来源/版本/采用/范围；产品规则与阶段决定不由检索模块生成或改写。

**必要满足条件：** 模块全集与需求/数据流一致；每个模块完成第 4 节卡片；无责任空洞或相互冲突；划分粒度与风险有理由，模块依赖图可复核。

## 4. 每模块技术设计卡

# SOP 自检与复检

开发流程模式：由 `formsy-sop-workflow` / `flow context` 协调时，本模块提供内容规则与审查，不另设阶段或例行确认。沿已有任务授权推进；实质修订保存差异并复检，实际缺少用户决定或扩大授权才询问。下文文档确认字段仍只记录真实确认，不能用程序推进伪造。

依据原始要求审查当前版本，回答哪些内容已有支持、缺什么、哪些动作被阻塞及如何复检。可单独审查产品文档或技术文档，不要求先运行其他 Skill。只收到部分资料时，完成可检查部分，保留未提供的依据与检查边界。

统一 MCP 模式先按本模块审查通用 SOP 范围，使用 `workbench catalog/prepare/scaffold/record --profile general` 保存适用性、真实文档来源、逐项证据和四态。Server 的正式项目规则另用 `flow review-rules` 读取、`--profile server` 审查。缺 Task、grant 或 Server 规则时，仍完成可检查的通用文档内容，项目层保留未核对；通用回执不表示 Server 规范已满足。

统一流程的通用文档目录从下表原生 PC/TC/KB/TASK、安全、质量和领域规则生成，按当前阶段提供可审条目与延期义务。TraceAudit 的交付审计合同独立保留，仅在完成验收或当前材料出现真实运行、交付、关闭声明时激活；未来计划不触发未来运行证据要求。原生内容仍须逐对象走读，目录覆盖不等于完整语义审查。关键可行性事实的必要事先证据不能因阶段早而省略；缺证据保留未核查及实际依赖阻塞。

机器操作、声明触发、依赖复用和增量草稿见[阶段审阅接口](references/stage-review-contract.md)。先核对当前材料是否包含实际声明，以来源引文登记；不能漏报声明来规避审计。未变化结论仅在规则、来源及传递依赖版本相同后复用，保留原回执，不称新执行。草稿可分批保存，最终仍须通过完整 record 和阶段门禁。

## 选择模式与资料

## 审查

1. 固定原始要求、当前对象/规则/来源版本、所需证据层次和输入定位。从要求与交付范围核对完整对象集，必需但缺失的对象也建检查行。全集不明记录不足，不用现有段落充当全部需求。
2. 按适用规则做 L1 结构核查与 L2 内容走读；必要 L3 事实查证/目标环境试验以真实依据判断。逐条记录原条件、位置、实际发现、依据和所需层次；四态为满足、不满足、未核查、不适用＋理由。未知、缺环境、未实现或未决定不能记不适用。
3. 对照原意核查“需求→产品行为→技术承担→任务→验收”和反向来源。核查正常、异常、取消、重复与恢复的实际适用范围；验收断言应判断用户任务结果。知识已采用只说明允许用途，不能证明主张正确或阶段已确认。
4. 将发现分流为可查事实、用户取舍、行为假设、技术可行性、权限/预算/环境；列影响对象、被阻塞的具体动作、下一动作与关闭条件。按共同约定，模块开始时已知的待决定问题集中逐题展示，走读中新发现或冲突逐题补问，已有有效决定不重复询问。继续不依赖该缺口且已授权的工作。
5. 输出 [审查报告模板](assets/review-report-template.md) 中适用于当前任务的内容，附 [证据与问题卡](assets/evidence-issue-template.md)。没有工具时给内容和预期文件名，不能声称已保存或已运行。修订建议与实际修订分别记录。

JSON 交接可用 `python3 scripts/validate_handoff.py <交接文件>` 做可选结构检查。只有脚本实际可用并执行时记录其结果；脚本不证明证据真实、语义正确、阶段已批准或应用可运行，仍须执行对应内容核查。

统一入口已连接原子工作台时，先复核预加载条件是否漏选、错选及原子义务是否完整，给出新增、移除、保留与不确定项的理由。对入口提供的已选编译条件逐项比较原文，输出候选依据，由入口复用CLI保存引用校验回执；普通Markdown自检表不能充当这个回执。来源版本变化时说明差异并复检受影响项，缺工具或未编译的PC/KB范围明确列出，不伪造原子通过。独立文档审查仍按原输出工作，不强制安装或运行工作台。

条款齐全不代表业务旅程完整；沿各角色正常、失败、取消、重复、恢复路径检查设计与可观察验收的衔接。已采用决定变化后，核对产品、技术、任务、验收及引用影响是否处理；未决明确是定稿阻塞、可带条件交付还是开工前解决。旧文档确认不能直接用于新版本。

涉及状态或权限的动作，按实际前状态分别对照“主体/权限→动作→返回含义→后状态/副作用→技术/任务→验收前置及断言”，给出各端原文定位。不要只因有状态表、接口和AC编号就写一致；“申请成功”不能替代“业务完成”，“各非终态”等概括不能覆盖已经确认的不同分支。找到矛盾时记录受影响的实际义务为不满足并保留两端引文；修订后比较新旧分支再追加复检，未变化项明确复用边界。这是内容走读方法，不是自动语义检测器。

已加载、已审阅、缺证据分别记录。可从当前文档核查的L1/L2义务先比较具体对象和原文，不把所有未核查项统一推到开工任务。必须实测的义务仍保留未核查，写明所缺环境/输入/断言；补文档或人工声明不能代替实测。检查状态重置路径是否抹掉永久约束（如曾批准后须先取得变更许可），以及前任务的完成断言是否依赖后任务实现；跨模块断言放到依赖齐备的集成检查，不制造串行任务的隐性循环。

安全专项使用 `CUSTOM:SEC01`–`CUSTOM:SEC12`，与 TC09/TC10、相关 KB 规则交叉追踪，不覆盖其原定义、不凭增加检查行提高分数。先固定资产/边界和适用对象，核对每个风险的控制、实施责任、反例及所需证据。安全文档完整、措施已实现和当前构建测试有效分别判断；未知配置/加密方案、未查漏洞、无运行证据不记通过或不适用。只审阅文档时不执行攻击、扫描、敏感数据外发或系统权限变更。

## 复检与关闭

保留原发现、失败、关闭历史和旧版本绑定。沿真实依赖确定修订影响，复检原对象和受影响对象；无影响证据复用需给理由，不把旧运行记录称为新重测。关闭须回答原条件、取得该问题要求的当前证据与必要用户决定。补计划只关闭计划缺失；暂停、环境恢复、移交或补台账不关闭未验证行为。

来源、要求、方案、权限、平台、配置或规则变化，以及反例/复发/错误关闭，触发重开或证据失效评估。自动修订/重试仅在有效已确认范围、权限和预算内有界进行；需要实质变更时展示差异后等待相应决定。停止保留检查点和开放问题；恢复先核对版本、许可、环境、预算和已产生副作用。

## 可选评分与结论

评分先固定 PM/M 对象全集与规则展开，报告每维 `T/S/F/U/N/A`、权重、证据和非满足项。`A=S+F+U`；缺环境仍在分母。全集或展开未确定时该维及总分留空，不以满分代替。仅在全部维度可计算、排除已复核且有效权重大于零时按量表归一化。95 分是资料中的拟议文档门槛；只有本项目实际采用后才用于判断，不自动套用历史应用目标。

并列报告文档设计检查、自检方法效果、用户价值支持、阶段确认、实际应用验收。关键阻塞不被分数抵消。真实应用通过须有当前构建/平台操作、全部断言与相应文件/日志/截图；缺 Windows 环境记未验证/环境阻塞并保留适用分母。只审查文档时实际运行保持未执行；模型自评或合成示例不作为独立真值。
