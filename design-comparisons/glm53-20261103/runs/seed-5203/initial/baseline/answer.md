# 产品 SOP：对话式数据分析工具「修改与删除历史问题」

## 0. 文档说明

本文档为产品行为设计与实施计划，**不涉及代码实现**，所有内容均为设计阶段产出，尚未开发、测试或上线。文中明确区分：

- **【已明确】**：需求方在开发请求中已规定的行为
- **【建议】**：设计建议，待需求方确认
- **【待定】**：需求方必须补充决定的事项

---

## 1. 需求范围

### 1.1 已明确的需求

1. 用户可**修改**历史问题：修改后，结合之前的对话上下文重新生成回答。
2. 用户可**删除**历史问题：删除该问题及其后续回答，并更新对话历史。

### 1.2 范围外（本次不做）

- 【建议】不涉及多用户协作编辑同一会话（单用户操作为主）。
- 【建议】不涉及回答内容的单独编辑（只编辑问题文本）。
- 【建议】不涉及跨会话的批量删除。

---

## 2. 用户可操作的位置与行为

### 2.1 操作入口

| 位置 | 可执行操作 | 状态 |
|---|---|---|
| 历史问题气泡（hover 或常驻菜单） | 修改、删除 | 【建议】hover 显示操作图标，移动端长按呼出菜单 |
| 最新一条问题 | 修改、删除 | 【建议】与历史问题一致，保持交互统一 |
| 回答气泡 | 不可修改、不可单独删除 | 【已明确】删除以问题为单位，回答随问题处理 |
| 图表 | 不可单独删除 | 【建议】图表属于回答的一部分，随回答删除/失效 |

### 2.2 修改行为

- 【已明确】点击修改后，问题文本进入可编辑状态（建议：在原位置编辑，而非跳到输入框）。
- 【已明确】保存后，系统基于**该问题之前的对话上下文 + 修改后的问题**重新生成回答。
- 【建议】修改后的问题替换原问题，原回答被新回答替换；原回答是否可查看（如折叠的“历史版本”）→ **待定**（见第 8 节）。

### 2.3 删除行为

- 【已明确】删除某问题时，**该问题及其之后的所有问答**一并删除。
- 【建议】删除前弹出确认框，明确提示：“将删除此问题及之后的 N 条问答”。
- 【建议】删除后，对话停留在被删问题的前一条问答之后，输入框获得焦点，用户可继续提问。

### 2.4 修改/删除后各元素的变化

| 元素 | 修改后 | 删除后 |
|---|---|---|
| 被修改的问题 | 文本更新为新问题 | 不存在 |
| 该问题的回答 | 重新生成，替换旧回答 | 随问题删除 |
| 该问题的图表 | 随新回答重新生成（或按新回答决定是否出图） | 随回答删除 |
| 后续问答 | 【建议】标记为“基于旧版本生成”，需用户确认是否级联重算（见 4.2） | 全部删除 |
| 后续图表 | 同后续回答处理 | 全部删除 |

---

## 3. 对话历史与 Agent 上下文一致性

### 3.1 核心原则

【建议】Agent 实际使用的上下文必须**从对话历史实时派生**，而非维护一份独立的上下文快照。历史即唯一事实来源（Single Source of Truth）。

### 3.2 一致性规则

1. **修改**：上下文重建时，被修改的问题以新文本参与；其后的问答是否参与取决于级联策略（见 4.2）。
2. **删除**：上下文重建时，被删问题及其后所有问答完全不参与；Agent 下一次回答只“看到”删除点之前的对话。
3. **图表引用**：【建议】若后续回答中引用了被删/被改回答的图表编号或结论，级联处理时需重新生成，避免“幽灵引用”。

### 3.3 重建时机

- 【建议】采用**惰性重建**：修改/删除时只更新历史记录，下一次用户提问时再按当前历史重建上下文。优点是实现简单、避免删除后立即触发大量重算。
- 【备选】立即级联重算后续所有回答。体验更一致但成本高。
- → **待定**：需求方需在“惰性重建 + 标记提示”与“立即级联重算”之间选择（见第 8 节）。

---

## 4. 状态设计

### 4.1 问题/回答状态机

```
问题状态：normal（正常） → editing（编辑中） → regenerating（重新生成中） → normal
         normal → deleting（确认中） → deleted
回答状态：normal → regenerating → normal
         normal → stale（旧版本标记，若采用惰性策略）→ normal / deleted
```

### 4.2 级联策略（关键待定项）

| 策略 | 行为 | 优缺点 |
|---|---|---|
| A. 惰性 + 标记 | 修改/删除后，后续问答标记为 stale，不立即重算；用户下次提问时 Agent 只用有效上下文 | 成本低；界面有“过期”标记 |
| B. 立即级联重算 | 修改后自动重新生成所有后续问答 | 体验一致；成本高、可能级联很长 |
| C. 用户选择 | 修改后弹窗询问“是否重新生成后续回答” | 灵活；多一步交互 |

→ **待定**：需求方必须选择。**【建议】** 初版采用 A（惰性 + 标记），后续迭代再评估 B/C。

---

## 5. 角色与权限

| 角色 | 修改 | 删除 | 范围 |
|---|---|---|---|
| 会话所有者 | ✅ | ✅ | 本会话内所有问答 |
| 【建议】只读分享对象 | ❌ | ❌ | 仅查看 |
| 【建议】管理员 | ❌（不代用户改） | ✅（合规/审计场景可删） | 待定 |

- 【建议】仅会话所有者可操作；分享链接接收者默认只读。
- 【待定】是否存在团队共享会话、管理员删除权限、操作审计日志要求。

---

## 6. 数据与上下文定义

- **对话历史**：有序问答序列，每条含：问题文本、回答文本、图表引用、时间戳、版本号。
- **版本**：【建议】修改不覆盖原始记录，而是新增版本（version++），便于审计与“查看历史版本”功能（是否暴露给用户 → 待定）。
- **删除**：【建议】软删除（标记 deleted，可审计），用户界面不可见。是否物理删除 → 待定（涉及数据合规）。
- **图表**：作为回答的附属资源存储，随回答状态联动。

---

## 7. 正常路径、异常路径与验收

### 7.1 正常路径

**修改：**
1. 用户 hover 问题 → 点击“修改” → 进入编辑态
2. 修改文本（如“华东”→“华南”）→ 保存
3. 该问题显示新文本，回答进入 regenerating → 新回答（含新图表）替换
4. 后续问答按选定级联策略处理
5. 下次提问时，Agent 上下文与界面历史一致

**删除：**
1. 用户点击“删除” → 确认框提示影响范围（“将删除此问题及之后 N 条问答”）
2. 确认 → 该问题及后续问答从界面消失
3. 下次提问时，Agent 不感知被删内容

### 7.2 异常路径

| 异常 | 处理 | 状态 |
|---|---|---|
| 修改后重新生成失败 | 保留旧回答 + 显示错误提示 + “重试”按钮；问题文本已更新 | 【建议】 |
| 修改后问题为空/超长 | 前端校验，禁止保存 | 【建议】 |
| 删除时网络失败 | 界面不变，提示失败 | 【建议】 |
| 重新生成中用户再次修改/删除 | 【建议】禁止并发操作，或取消前次任务；→ 待定 |
| 修改后问题与数据集不匹配（如问不存在的维度） | 走 Agent 正常“无法回答”路径 | 【建议】 |
| 会话被他人分享中时删除 | 【建议】只读方看到的历史同步更新；→ 待定 |

### 7.3 验收标准

**修改：**
- AC1：修改第 2 个问题后，该问题文本更新，回答基于“问题 1 + 新问题 2”重新生成。
- AC2：新回答中不再包含旧回答的图表；图表与回答一致。
- AC3：后续再次提问时，Agent 回答体现修改后语义（如后续问“它的占比”，应基于华南数据）。
- AC4：修改过程中刷新页面，历史不出现半成品状态（要么旧、要么新）。

**删除：**
- AC5：删除第 2 个问题后，第 2、3 条问答（含图表）全部消失，第 1 条保留。
- AC6：删除后再提问，Agent 回答不引用被删内容（如不提“华东产品”）。
- AC7：删除确认框准确显示影响条数。
- AC8：删除最后一条问答后可正常继续提问。

**通用：**
- AC9：界面显示的历史与 Agent 实际使用的上下文一致（可通过追问验证）。
- AC10：只读角色看不到修改/删除入口（若采纳权限建议）。

## 8. 需求方必须补充决定的事项（待定清单）

| # | 待定项 | 选项/问题 |
|---|---|---|
| 1 | 级联策略 | 惰性+标记 / 立即重算 / 用户选择（4.2） |
| 2 | 旧回答是否保留可查 | 修改后旧回答是否作为历史版本折叠展示 |
| 3 | 删除方式 | 软删除（可恢复/审计）还是物理删除；是否需要回收站 |
| 4 | 权限模型 | 是否存在分享、团队会话、管理员角色 |
| 5 | 并发操作 | 重新生成中是否允许继续修改/删除 |
| 6 | 图表独立操作 | 是否需要单独“重新生成图表”入口（本次建议不做） |
| 7 | 审计日志 | 是否记录谁在何时修改/删除了什么 |
| 8 | 移动端交互 | 长按菜单等移动端方案是否纳入本期 |

## 9. 制作任务计划（不含代码实现）

| 阶段 | 任务 | 产出 | 依赖 |
|---|---|---|---|
| 1. 需求确认 | 与需求方逐项确认第 8 节待定项 | 确认记录 | 无 |
| 2. 详细设计 | 状态机图、交互稿（修改/删除/确认框/stale 标记）、上下文重建规则文档 | 设计文档 + 原型 | 阶段 1 |
| 3. 数据模型设计 | 问答版本结构、软删除标记、图表关联关系 | 数据模型文档 | 阶段 2 |
| 4. Agent 上下文方案 | 历史派生上下文的规则说明、级联策略落地方式 | 技术方案文档（不实现） | 阶段 2 |
| 5. 验收用例编写 | 按 AC1–AC10 细化为可执行测试用例 | 验收用例集 | 阶段 2 |
| 6. 评审 | 产品 + 工程 + 需求方三方评审 | 评审结论 | 阶段 3–5 |
| 7. 排期与开发交接 | 任务拆解、里程碑 | 实施计划 | 阶段 6 |

**里程碑建议**：需求确认（第 1 周）→ 设计完成（第 2–3 周）→ 评审通过（第 4 周）→ 进入开发排期。

---

## 10. 风险提示

- 【建议】级联重算在长对话中成本高、耗时长，需在阶段 1 优先确定策略。
- 【建议】“历史即事实来源”的架构若与现有实现冲突，需工程评估改造成本。
- 【建议】软删除与数据合规（用户数据删除权）需法务/合规确认。
